## Notes

- **One connection to the event stream per page** (`use-stream.ts`). A view never opens its own: it reads a slice of the live state with `useStream(select)`, or follows the ledger with `useLiveRead(route, kinds)`, which reads a dev-only route on mount and again when an event of one of `kinds` is applied, or `useOperatorRead(path, kinds)`, the same for an operator API read route (`/__agent-forge<path>`, its envelope unwrapped, an `ok: false` answer an error in the hearth's words). `useOperatorRead` also returns a `reload`, for a view that just changed something: an `operator.action` event is appended before its effect, so a read it triggers can come too early (the Workbench reads again after each answer). Pass `kinds` as a module constant. The app root holds one subscription for the life of the page (`LiveBanner` in `app.tsx`), so moving between routes does not close the connection.
- The rules that turn a snapshot and its deltas into state are pure functions in `app-state.ts` (`applySnapshot`, `applyDeltas`, `liveStats`), and the session and reservation folds there mirror `listSessions` and `activeReservations` in `scripts/ledger/query.ts`: change both sides together. Runs and the queue are not folded from events; their read routes are fetched again on the event kinds named in `use-stream.ts`. A session is folded, but one the list holds no row for whose `session.started` is not in the batch (a session older than the snapshot's newest 100 that speaks again) has a row made from one event; `sessionsWithoutRow` names it before the batch is applied, and `createStreamClient` then reads `/sessions?limit=500` (after showing the delta, one read per burst) and `withSessionRows` fills only the fields the held row lacks (start, kind, worktree, parent, executor, bead, run), never replacing the list or the held row's times, since events applied while the read was in flight are newer. The sessions route has no per-session parameter.
- The stream is read with `fetch`, not the browser's event-source class: the hearth takes the resume id only as the `Last-Event-ID` request header, which a page cannot set on a connection that class opens. Reads of the stream and of the operator API's read routes send no operator token.
- The one read that does is a stored council run (`islands/CouncilIsland.tsx`: the run list, a run, a run's progress stream), which the hearth answers only with the token (`x1gs.7.7`). Make it with `operatorRead` (`operator.ts`), which shares the page's token cache with `operatorPost` and, after a 403, fetches the token again and reads once more; follow a run's stream with `fetchTransport(url, { fetch: operatorRead })`, never the browser's event-source class, which cannot send the header.
- The Council page follows a running council with `followCouncilRun` (`council-run-follow.ts`, `bj90`), which the island calls with `fetchTransport(councilRunEventsUrl(…), { fetch: operatorRead })`. The URL carries `?deltas=1`: the hearth sends the whole job once (`snapshot`) and then what changed (`delta`, `scripts/council/job-delta.ts`), or a whole job again when an update is not the job before plus appended entries, so both listeners stay. The job is rebuilt with `applyCouncilJobDelta` from the job **that connection** last received, which the follower holds; never apply a delta to the island's `job` state, which a run opened from the history or a re-read can replace in between (a delta applied to another job repeats or loses entries). A delta that cannot be applied (no whole job held on the connection, which is also the case after a whole job that could not be read or was another run's; another run's delta; unreadable; or not what follows the job held: its first event must be the next number after the last one held, the rest one by one, and none of its rounds one already held, so a delta sent twice or out of order is refused) closes the connection, reads the run again and follows it from a new whole job. The held job belongs to the connection, and so does "closed": a message from a connection that is no longer the current one is ignored. Reads in a row (a stream that stopped, a delta refused) are capped at `MAX_FALLBACKS`; a connection that delivers a second good message starts the count again, and past the cap the page shows the connection-lost text and stops following until it is refreshed. The follower is a pure module (transport, run read and timers injected); `scripts/dashboard/council-run-follow.test.ts` drives it with a stand-in stream and once against the hearth's real route, and `tests/e2e/council-stream-deltas.spec.ts` follows a simulated run in the browser.
- Send to council (`islands/SendToCouncil.tsx`, `x1gs.7.2`) is a link to the Council page with the bead preselected (`council.html?sourceType=bead&source=<id>`), on the issue detail panel (a button), each forge-run checkpoint and each Workbench card (a text link labelled `Send <id> to council`). The page's own profile picker, budget, evidence preview (a bead is shown before it is sent), Convene and run stream do the rest, and the hearth posts the verdict back to the bead when the run completes. Do not start a run from another view or build a second picker.
- An answer that is not an event stream (a static host) turns live updates off after one request, for the life of the page; a failure is retried with a jittered, doubling wait (each a random half to all of 0.5, 1, 2, 4 and 8 s) and gives up after six in a row. A request that gets no answer (no response headers) within 10 s (`ANSWER_MS`) is a failure: a hearth that hangs never answers. The hearth writes a comment (`: open`) as soon as a stream opens, because behind the dashboard's proxy the headers reach the page only with the first byte of the body; without it a resume opened 15 s after the request, with the first keepalive. A first open must deliver a valid snapshot within 20 s (`SNAPSHOT_MS`, the 15 s queue read plus 5 s margin); comments and partial messages do not extend that absolute deadline or reset failures. Six first opens that only send `: open` give up within 135.5 s including retry waits when the `: open` byte comes at once; the 20 s runs from the open, so a hearth whose `: open` comes just inside the 10 s answer limit is given up after about 195.5 s at most. After a snapshot, or on a resume, an open stream that sends nothing for 45 s (`SILENCE_MS`, three keepalives) is a failure. A hearth that never answers is given up after six answer limits and the waits between them: 75.5 s at most. A connection counts as working, and the count starts again, only when it has been open for 5 s and is then heard from (a delta or a keepalive); the `: open` byte comes at the open, so it never resets the count, and a stream that stays silent never does either. A hearth started before the `: open` byte existed (one that outlived a dashboard restart, which the dashboard attaches to again) answers an idle resume, behind the proxy, only with its keepalive at 15 s, past the answer limit; so a resume that gets no answer is asked for next without its id, and a first open answers with its snapshot (one failure, then live again). A static copy (a `vite build` of the dashboard) asks the hearth for nothing: a build has no HMR socket (`import.meta.hot` is undefined there; `servedStatically()` in `hearth-read.ts` is the one switch) and no hearth behind it. It asks for no stream (`pageTransport`), so live updates are off from the start; and its other reads (`pageReads()` in `use-stream.ts`, which `useLiveRead`, `useOperatorRead`, the Timeline and the stream client's own reads pass; `useDevApi`; the page's `beadWrites` and the page's operator client, which fetches the token) fail at once with `STATIC_COPY_ERROR` and send nothing. Each view then shows what it shows for a failed read. A new page-level read passes the switch too: the read functions take it as an option, off by default, because `import.meta.hot` is undefined under `bun test` as well. Nothing polls on a timer, and nothing is logged per event. A page must keep working with live updates off: `useLiveRead` still does its first read, and anything drawn from the live state is absent, not broken.
- **Every read of the hearth has a time limit** (`readHearth` in `hearth-read.ts`, which has no package import because `operator.ts` uses it; `READ_TIMEOUT_MS`, 45 s, over the answer and its body): `readOperatorRoute`, `fetchDevApi` and the bead actions' options read all go through it. A hearth that hangs never answers; past the limit the request is aborted (its connection dropped) and the read fails, so a view without data shows its error state and one with data keeps it (`startLiveRead`), and the refetcher's one read in flight is over, so the next event reads again. 45 s is above the 30 s the hearth gives any one `bd` call, so a late answer still comes in the hearth's own words. The launch exchange, operator token fetch, operator posts and council run reads (`operator.ts`) reuse that same deadline over headers and body. A token timeout fails as `NotSent`; a sent post timeout has an unknown outcome and is never automatically retried. Nor is it offered again blind: a view that posts an action says what such a failure means with `bead-writes.ts`, `moveOutcome` (`workbench-model.ts`) or `actionOutcome` (`action-outcome.ts`, the council start and cancel and the checkpoint review), says how to check, and holds the action until it has read the state again (the Council page reads the runs list) or the operator says they have checked (the review). Only an explicit 403 permits the existing single retry. Ordinary answers are buffered under the deadline; a requested SSE answer stays streaming, with only its headers bounded here and caller cancellation retained for its lifetime.
- A new component that reads the stream is a pure view plus a thin wrapper that calls the hook (`islands/LiveStatus.tsx`), so the view is testable as a plain function.
- The dashboard's Beads cards (`islands/BeadCounts.tsx`) read `GET /beads/counts` with `useOperatorRead` and follow `bead.transitioned`. They show the tracker's counts while every initiative is shown (the route counts the whole tracker), and the snapshot's with an initiative chosen, before the hearth has answered, and where none answers (a static copy does not ask). A write made with `bd` outside the hearth records no event, so the cards show it at their next read. The dashboard's two stat rows are mounted without a snapshot as well (`app.tsx`); each is absent where it has nothing to show.
- Completed bead-source council results show verdict-comment status (`CouncilVerdictStatus.tsx`) independently of the completed review. The stored source locator names the bead. Its exact-bead, workspace-scoped `/events` read follows `council.verdict.comment` on the page ledger stream, so a comment outcome arriving after the council progress SSE ended still appears. Only the matching run at/after its start can supply an outcome; missing, unreadable or omitted metadata stays status not known. No polling or automatic comment retry. The child is keyed by run/start/bead to discard stale reads when another review opens.
