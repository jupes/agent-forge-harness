## Notes

- **One connection to the event stream per page** (`use-stream.ts`). A view never opens its own: it reads a slice of the live state with `useStream(select)`, or follows the ledger with `useLiveRead(route, kinds)`, which reads a dev-only route on mount and again when an event of one of `kinds` is applied, or `useOperatorRead(path, kinds)`, the same for an operator API read route (`/__agent-forge<path>`, its envelope unwrapped, an `ok: false` answer an error in the hearth's words). `useOperatorRead` also returns a `reload`, for a view that just changed something: an `operator.action` event is appended before its effect, so a read it triggers can come too early (the Workbench reads again after each answer). Pass `kinds` as a module constant. The app root holds one subscription for the life of the page (`LiveBanner` in `app.tsx`), so moving between routes does not close the connection.
- The rules that turn a snapshot and its deltas into state are pure functions in `app-state.ts` (`applySnapshot`, `applyDeltas`, `liveStats`), and the session and reservation folds there mirror `listSessions` and `activeReservations` in `scripts/ledger/query.ts`: change both sides together. Runs and the queue are not folded from events; their read routes are fetched again on the event kinds named in `use-stream.ts`.
- The stream is read with `fetch`, not the browser's event-source class: the hearth takes the resume id only as the `Last-Event-ID` request header, which a page cannot set on a connection that class opens. Reads of the stream and of the operator API's read routes send no operator token.
- The one read that does is a stored council run (`islands/CouncilIsland.tsx`: the run list, a run, a run's progress stream), which the hearth answers only with the token (`x1gs.7.7`). Make it with `operatorRead` (`operator.ts`), which shares the page's token cache with `operatorPost` and, after a 403, fetches the token again and reads once more; follow a run's stream with `fetchTransport(url, { fetch: operatorRead })`, never the browser's event-source class, which cannot send the header.
- An answer that is not an event stream (a static host) turns live updates off after one request, for the life of the page; a failure is retried with a jittered, doubling wait (each a random half to all of 0.5, 1, 2, 4 and 8 s) and gives up after six in a row. A connection that sends nothing for 45 s (three keepalives) is a failure, timed from the request: a hearth that hangs never answers. Behind the dashboard's proxy, the answer arrives only with its first byte, which on a resume is the keepalive 15 s after the request, so the limit must stay above that. A connection counts as working, and the count starts again, only when it has been open for 5 s and is then heard from (a delta or a keepalive); a stream that stays silent never resets it. A static copy (a `vite build` of the dashboard) asks the hearth for nothing: a build has no HMR socket (`import.meta.hot` is undefined there; `servedStatically()` in `hearth-read.ts` is the one switch) and no hearth behind it. It asks for no stream (`pageTransport`), so live updates are off from the start; and its other reads (`pageReads()` in `use-stream.ts`, which `useLiveRead`, `useOperatorRead`, the Timeline and the stream client's own reads pass; `useDevApi`; the page's `beadWrites` and the page's operator client, which fetches the token) fail at once with `STATIC_COPY_ERROR` and send nothing. Each view then shows what it shows for a failed read. A new page-level read passes the switch too: the read functions take it as an option, off by default, because `import.meta.hot` is undefined under `bun test` as well. Nothing polls on a timer, and nothing is logged per event. A page must keep working with live updates off: `useLiveRead` still does its first read, and anything drawn from the live state is absent, not broken.
- **Every read of the hearth has a time limit** (`readHearth` in `hearth-read.ts`, which has no package import because `operator.ts` uses it; `READ_TIMEOUT_MS`, 45 s, over the answer and its body): `readOperatorRoute`, `fetchDevApi` and the bead actions' options read all go through it. A hearth that hangs never answers; past the limit the request is aborted (its connection dropped) and the read fails, so a view without data shows its error state and one with data keeps it (`startLiveRead`), and the refetcher's one read in flight is over, so the next event reads again. 45 s is above the 30 s the hearth gives any one `bd` call, so a late answer still comes in the hearth's own words. The operator token fetch, operator posts and the council's run reads (`operator.ts`) have no limit of their own.
- A new component that reads the stream is a pure view plus a thin wrapper that calls the hook (`islands/LiveStatus.tsx`), so the view is testable as a plain function.
- The dashboard's Beads cards (`islands/BeadCounts.tsx`) read `GET /beads/counts` with `useOperatorRead` and follow `bead.transitioned`. They show the tracker's counts while every initiative is shown (the route counts the whole tracker), and the snapshot's with an initiative chosen, before the hearth has answered, and where none answers (a static copy does not ask). A write made with `bd` outside the hearth records no event, so the cards show it at their next read. The dashboard's two stat rows are mounted without a snapshot as well (`app.tsx`); each is absent where it has nothing to show.
