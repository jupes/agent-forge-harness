# Provider readiness and usage boundary

Bead: agent-forge-harness-cla5.6.1. Keep executable discovery, version response, authentication, adapter support and usage reporting as separate facts. `doctor().ok` proves only that a version command answered. The registry currently supplies Claude and Codex; five names in the design do not establish five working adapters.

## Interface alternatives

**One protected capability report.** A bounded server report collects independent typed observations, their source and read time. One desktop read store supplies Providers, title bar, home and composer consumers. Vendor probes remain behind fixed adapters and timeout/environment controls. Locally counted tokens/cost, provider allowance windows and API balances retain distinct units and provenance. Unknown facts remain unknown. This is the selected interface: it makes one authority and normalization boundary serve every consumer.

**Independent per-card probes.** Each card and meter could call vendor status or existing session options directly. This makes simple cards quick to build, but duplicates probes, creates conflicting read times and tempts version success or an environment key to become sign-in evidence. It also lets the home meter disagree with the provider page.

**One ranked availability number.** A server could collapse all observations into a headroom score or preferred provider. That hides units, subscription windows versus API balances and uncertainty, and would imply automatic routing that the brief forbids. Reject this shape.

## Evidence and limits

The report must identify executable discovery, version/doctor result, actual reported authentication route, adapter support and each supported usage measure separately. No credential value reaches the renderer. An API-key variable being present does not prove that it works. A configured smith is not an authenticated account. No paid doctor task, real account call, credential-file read or real provider execution is used as a test fixture.

Reported-used and reported-remaining measurements normalize once at this boundary. The source basis stays explicit. Without a known total, the opposite quantity and percentage stay unknown. Local ledger counts never become provider allowance or a cross-provider headroom ranking. Missing reset times and costs remain absent; stale observations remain labelled. Rechecking data and opening a vendor sign-in flow are separate operations with their own authority and outcomes.

OpenRouter's settled later OpenCode/ACP route remains deferred; readiness must show that limitation rather than introduce another provider route. Gemini and Grok capability comes from their actual adapter delivery, not their card's presence.

## Delivered report and refresh

It refreshes the coalesced report using fixed non-generating checks; it cannot accept a task, arbitrary command, provider request, credential or file path. Neither route calls `forge:doctor --task`.

`createProviderInspector` discovers the named CLI, checks `--version`, then uses only `claude auth status` or `codex login status` where the status interface is supported. Other adapters remain unavailable. Each process has a three-second bound, 64 KiB line bound and 128 KiB aggregate output bound, filtered configured environment and supervised tree cleanup. Account identities, raw stdout/stderr and credentials never enter the report. The operator token is stripped even when present inside a differently named passed environment value.

The compatibility floor is the status interface this implementation targets (Claude2.1.293 and Codex0.163.0), not a claim about the earliest vendor release that could run a task. No paid request is used to check them.

## Native sign-in interface alternatives

**Protected fixed-command console launch (selected).** The existing operator action boundary audits a strict provider and UUID, then retains an immutable private attempt before one native launch. Windows starts the fixed vendor executable and fixed login arguments in a new console, initially suspended. An existing kill-on-close job must own it before its first thread resumes; failed supervision refuses before the CLI runs. The renderer receives metadata and never terminal input/output. Closing the app ends its login child tree. Explicit status rechecking remains a separate action and terminal exit0 never asserts sign-in. A restarted hearth reads the original intent without launching it again.

**A compiled terminal wrapper.** A separate sidecar could launch the fixed CLI using a native console. It adds another packaged executable, startup handshake and ownership boundary; the wrapper can spawn before the hearth assigns its job unless another suspended-process protocol is added. The existing Bun Windows native boundary already provides the required job mechanism.

**Direct renderer-to-native login invocation.** A Tauri command could open the terminal. It would add remote-page IPC permissions and another approval/audit channel beside the protected operator API. Keeping this effect in the existing operator table gives every caller the established origin/token/validation/audit order and one durable original identity.

The native launcher accepts trusted executable/argv/cwd/environment data only from its server-side fixed-provider preparer. Public input cannot supply command text, a shell, working directory, environment or credentials. Tests use inert processes, a private temporary home and synthetic arguments; the visible native path is checked separately from the pure and hidden-process fixtures. Windows x64 is the current packaged target; other platforms keep a specific unavailable control with the vendor command.

Native evidence references: Microsoft [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [console creation](https://learn.microsoft.com/en-us/windows/console/creation-of-a-console) and [job assignment](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject). A new console supplies the vendor's own I/O, Unicode environment is explicitly encoded, handles are not inherited, and suspended creation permits mandatory job assignment before execution.

## Native login identity and ownership

The action rows accept only a supported provider and UUID, or an empty Stop body. Origin, operator token, strict validation and the audit row precede every effect. Protected list and original reads expose metadata only. One immutable original/attempt marker is written owner-only before native launch. Repeating that UUID reads its original, never another launch. Exit0 means only that the terminal closed; authentication still needs an explicit doctor check.

Receipts are scoped to the canonical checkout under the private home, with256 retained identities and262,144 bytes, no eviction. Corrupt, future and full stores refuse and preserve their bytes. Each provider folder component is checked against links. A separate SQLite exclusive lease is provider-wide in that private home, so two workspaces cannot sign in to the same vendor simultaneously. The lease stays held until native job cleanup and the terminal receipt finish. OS owner death closes both the job and lease. A recreated service projects an old active record as Unknown while its lease is held, or Interrupted when the lease is free; it never replays that request. A new explicit sign-in can acquire a free provider lease. Stop controls only the in-memory owned child, never a persisted PID.

Fixed native.exe preparation rechecks the CLI/version and passes only base OS environment variables with harness/operator values removed. API keys and configured pass-through values are not inherited for login. Script shims and unsupported/native-incompatible routes retain their vendor command and explicit reason. The15-minute deadline, Stop, clean completion and abrupt host death end owned helper processes. An inert FFI-created helper regression proves completion cleanup independently of Bun's own exit hook. The actual default visible console is verified with GetConsoleWindow, without capturing any terminal I/O. Additional native tests prove abrupt host death releases the provider lease and ends both CLI and descendant before a fresh explicit sign-in. All verification uses inert processes; no real account or provider task is invoked.

The renderer saves and reads back only a hashed workspace identity, provider and original UUID under an origin WebLock before POST. Reload, a missing original, transport failure and malformed replies retain that identity. Only an explicit original retry can repeat the same fixed-provider request; it cannot mint another flow. A matching protected Closed/Interrupted receipt permits release; failed erasure retains the hold. Another window adopts the same identity and its Stop result updates the original window. ## Actual owned-session allowance

Only the verified `claude.usage_report` fields supply current allowance: explicit0–100 `percent`, ISO `resets_at`, and `is_active:true`. Unknown/inactive windows, a newer missing report, a changed CLI version or a later sign-in withhold earlier allowance. Numeric rate-limit utilization/reset units, plan/account identity and window duration are unreported and never inferred. Source/version/local receipt time remain visible; continuity with the current account is not proved by these fields.

The protected source examines at most the newest32 owned Claude sessions in this workspace, with an8MiB preflight scan budget and a2-second admission budget between bounded full-journal reads. One journal growing after its size check can add at most the existing8MiB per-journal read cap. It validates the original provider/version-bound private state, never parses a raw provider log or contacts an account endpoint. Older/unscanned reports can be absent and this limitation is displayed. Corruption withholds the account source; counted local history remains separate.

A provider-wide private sign-in marker is persisted before native launch, so a login in another workspace also invalidates earlier allowance. The coalesced cache and in-flight reads bind the unique marker UUID plus the explicit doctor generation. If either changes while a report is being built, that result cannot publish; bounded retries read the current generation. Both stale-cache and held-scan regressions fail before this protection and pass afterward.
