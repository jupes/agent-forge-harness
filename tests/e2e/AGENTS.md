# AGENTS.md — tests\e2e

The browser suite for the dashboard: `bun run verify:ui` (Playwright, Chromium, a desktop and a mobile project).

## Scope

- Applies to this directory and descendants unless a deeper `AGENTS.md` overrides it.
- Parent guidance still applies unless this file states a stricter override.

## Local Rules

- Keep edits focused on files within this subtree.
- Follow repository-level quality gates before shipping. The suite also runs on every pull request (`e2e` job in `.github/workflows/quality.yml`), where a red suite shows as a failed Playwright check. That check is not a required status check on `master`, so GitHub will still let the PR merge: treat red as blocking yourself.
- **Fixtures are typed against the real API.** Everything in `fixtures.ts` is held to its model type with `satisfies` (`ForgeRunSnapshot`, `ReposKnowledge`, `BeadsPayload`). When an endpoint changes shape, `bun run typecheck` fails here. Do not loosen a fixture to `Record<string, unknown>` or cast it to get past that; update it.
- **A request to the hearth's operator API is made from page context** (`page.evaluate` with `fetch`, or the page's own code), not with the runner's `request` fixture: the API answers only a declared same-origin request, and the runner's requests carry no `Origin`. The hearth is the real one (`main()`), but its `bd` is the suite's recording stand-in (see Servers): `GET /queue` and the stream snapshot get an empty list from it, here and in CI.
- **No test may depend on this machine's state.** `docs/data/beads.json`, `.tmp/work/forge-runs/`, `repos/` and the quality-gate log are generated or gitignored, and a fresh clone (which is what CI gets) has none of them. Serve a fixture through route interception (`stubSnapshot`, `stubForgeRun`, `stubRepos`), or, for a test that reads the real API on purpose, assert only what the API just returned.
- **Do not skip a test because data is missing.** A conditional `test.skip` on missing data never runs in CI. A normal run reports zero skipped; a skip means something is wrong and needs a Beads issue and a reason.
- A test that is not meant for every run is deselected in `playwright.config.ts`, not skipped at run time. A project's `grepInvert` replaces a top-level one, so each project lists everything it leaves out.
  - `@screenshot` (`screenshots.spec.ts`) writes image files. It is selected only when `SHOT_DIR` is set: `SHOT_DIR=.tmp/shots/after bun run verify:ui -- --grep @screenshot`. CI never runs it. Its only assertion is a visible heading, so look at the images after changing a fixture it uses.
  - `@mobile` tests assert a 375px layout. They run on the mobile project only.
- **Open a page with `openSettled(page, url)` and reload it with `reloadSettled(page)` (`fixtures.ts`), never with `waitUntil: "networkidle"`.** Every page of the app holds one request to the hearth's event stream open for as long as it lives, and the runner counts a streamed `fetch` as in flight, so its network-idle wait never ends there (a test using it runs to the 45 s timeout). The helpers wait for `load`, then until nothing but the stream has been in flight for 500 ms; requests of the previous document are forgotten on a navigation, and again when the new document commits (the old one runs until then and may start more, which the runner never reports as ended), so a reload with a request deliberately held unanswered still settles. `settle.spec.ts` tests that.
- **The stream is on in every spec.** The dashboard view shows a second stat row with live numbers from the suite's hearth (`data-testid="live-stats"`), so scope a locator for the Beads cards by label, not by position or count. A spec that needs the page without a stream answers the stream route itself (`live-stream.spec.ts` does, with what a static host answers, and with a server failure once, then the suite's hearth, or every time: the last runs through all six failures, 8 to 16 s of real retry waits, and sets its own timeout).
- **The Beads cards (`data-testid="bead-counts"`) show the stand-in tracker's counts** once the hearth has answered `GET /beads/counts` (`data-source="tracker"`), and a stubbed snapshot's before that or with an initiative chosen (`data-source="snapshot"`). A spec that needs the snapshot's numbers answers that route itself (`bead-counts.spec.ts`); a spec that reads the tracker's compares them with what the route just answered, since every spec of a run shares the stand-in's issues.
- **`live-stream.spec.ts` runs the real `forge:phase-gate … --write`** for a throwaway run (`live-run.ts`) while a page is open, and measures how long the page takes to show it. The command works in the checkout, because that is where the hearth reads run state: for the length of a test there is a run named `e2e-live-<pid>-<time>-<n>` with an artifact under `plans/research/` (and `plans/drafts/`) and a state file under `.tmp/work/forge-runs/`, all gitignored. The test removes them and asserts they are gone; teardown sweeps names of that shape that a killed run left, and they are safe to delete by hand. Its ledger events go to the run's own home. The command is given the hearth's environment without any `AGENT_FORGE_*` variable but the home, so nothing ties the run to a real bead or session. It refuses to run while a legacy `.tmp/work/forge-state.json` exists (the command would migrate it). Leave real forge runs in this checkout alone while the suite runs: a real phase write in the same second would be the newest run in flight, and the page would show that one instead.
- **`timeline.spec.ts` reads the real hearth's ledger, except in two tests.** A bead created and commented on through the bead builder has exactly three events under `bead=<id>`: the create's `bead.transitioned`, then the comment's `operator.action` and `bead.transitioned` (the create's `operator.action` names no bead, and operator writes carry no session, so nothing else joins). The kind-filter test also counts `/events` requests across a chip click and expects none. The 10,000-event test and the past-10,000 test serve `/events` themselves through `page.route`, answering any `after`, `limit`, `session` and `kind` as the hearth would. The past-10,000 test serves 10,005 events of one bead (a `session.started` first, a `verdict.bound` last) and asserts that the newest 10,000 are held, that the last event is reached, and that choosing `session.started` (counted 0 among those held) asks the ledger for that kind and shows its one event. It asserts that the document never holds more than the rows in view plus twice the overscan at any step of a scroll to the end, and that the last event is reached. It prints `[timeline-10k] …`: the time from the first read to the last answer, and the long tasks (over 50 ms, observed with `PerformanceObserver` from before the page's scripts run) while loading, while scrolling, and before the first read. Timing is not asserted; the bar is no long task while loading or scrolling. If a run shows long tasks, report the printed values. The test takes about 30 s per project and sets its own timeout.
- The one-second bound in that spec is measured from the ledger's timestamp on the event to an observer in the page, and each measured value is printed in the run's log (`[live-stream] … shown N ms after the ledger recorded it`). If it fails on a loaded machine, report the printed values; do not widen the bound.
- **`council-stream-deltas.spec.ts` follows a simulated run on the Council page** and compares what the page ends up showing (seats, discussion, report with its collapsed transcript, by `textContent`) with the same run opened as a bookmark (`?run=<id>`), which reads the run whole with no stream. The page asks for the run's stream with `?deltas=1`; a followed page also reads the run again when its stream ends while the run is going, which would hide a page that ignores every delta (it would end on the stored run all the same). So the tests that follow a run to its end assert the page made no read of the run (`GET …/runs/<id>`), and the fallback test answers the stream itself with a first job, a delta made for another run and then a failed job (`NEVER SHOWN`) that the page must not show: it closes that connection at the bad delta and reads the run once. The stream cannot be held open from `route.fulfill`, which is why that last message is how the test tells "read again at the bad delta" from "read again when the stream ended".
- New or changed tests are shown failing for the right reason before they count: break the thing under test, watch the test go red, restore it.

## Servers

- The config starts two servers, in order, and stops them afterwards: the hearth (`bun scripts/hearth/server.ts`, port 8798), then the dashboard (`bun run dashboard --strictPort`, port 8799), which attaches to that hearth. `control-plane.spec.ts` fails if the dashboard is proxying to any other hearth.
- A server that is already answering on either port is never reused; the run stops with an error naming the URL. It could belong to another checkout or to a hearth in your real `~/.agent-forge`. To run beside one, set `PORT` (dashboard) and `E2E_HEARTH_PORT` (hearth).
- What a busy port looks like:
  - something answering HTTP 200–403 there: `… is already used, make sure that nothing is running on the port/url`;
  - something answering with another status on the hearth port: `[hearth] Failed to start server. Is port 8798 in use?`;
  - the same on the dashboard port: `[dashboard] Error: Port 8799 is already in use`;
  - a listener that accepts connections and says nothing: no message at all. The runner's own availability check has no timeout, so it waits. If a run prints nothing for a while, check the two ports.
- Global setup stops the run when the runner was started with `NODE_USE_ENV_PROXY` on, `HTTP_PROXY` (or `http_proxy`) set and no `NO_PROXY` entry of `127.0.0.1` or `*`: Node's `fetch` then sends the helpers' requests to the hearth, operator token included, to that proxy (measured on Windows, Node 25.8.2; without `NODE_USE_ENV_PROXY` it goes direct). The rule is `loopbackProxyVariable` in `scripts/hearth/loopback.ts`. Whether the dashboard's own proxy to the hearth follows `HTTP_PROXY` then is not measured.
- Servers can outlive a run that was killed hard (the runner only stops them on a normal exit or Ctrl+C). Find and stop them by port, for example on Windows `netstat -ano | findstr :8798` then `taskkill /PID <pid> /T /F`, or use the two port variables for the next run.
- Each run gets a hearth home of its own, `agent-forge-e2e-<pid>-<time>` in the OS temp directory, removed when the run ends. It holds the hearth's lock and token, its ledger (`operator-api.spec.ts`, `council-bead.spec.ts` and `send-to-council.spec.ts` read what the hearth recorded there) and the artifacts of the simulated council runs those three specs start (per project, two from `operator-api.spec.ts`, one from `council-bead.spec.ts`, one from `send-to-council.spec.ts` and three from `council-stream-deltas.spec.ts`) (`COUNCIL_RUNS_DIR` points there, so nothing lands in `reports/`). The reason: the runner kills its servers outright, so a hearth never releases its lock, and a hearth started directly treats any lock with a live pid as a running hearth and exits (`agent-forge-harness-kt0q`). A home shared between runs would stop the suite from starting whenever an old lock's pid had been reused.
  - The home is left behind when a server fails to start or the run is killed, and on Windows after every run: teardown runs while the hearth still holds its ledger open, so the removal fails quietly. The next run's global setup removes it: every `agent-forge-e2e-<pid>-<time>` directory in the temp directory whose runner (that pid) is not running and whose hearth lock names no running process (`sweepFinishedRunHomes` in `run-homes.ts`, unit-tested in `scripts/dashboard/run-homes.test.ts`). It prints `[e2e] removed N hearth home(s) …` when it removed any. A home it cannot remove is left for a later run, and the sweep never stops a run. A home whose runner or hearth is alive may be another checkout's run in progress and is left alone. Such directories are also safe to delete by hand once their run is over.
  - `AGENT_FORGE_E2E_HOME` overrides the location, for inspecting what the hearth wrote. Teardown deletes a home only when its path has the generated shape (`agent-forge-e2e-<pid>-<time>` directly in the OS temp directory); it goes by that shape, not by who chose the path. Any other home is left alone, so the previous run's lock stays in it. That is harmless while the lock's pid is dead: the next hearth replaces it. Once that pid has been reused by any live process, the suite stops at start-up with `[hearth] hearth already running on …` and `Process from config.webServer exited early.` Empty the directory before reusing it.
- **The suite never reaches a tracker.** A hearth runs `bd` for a write, and the hearth here is the real one, so the `bd` it finds is not left to chance:
  - `bd-stand-in.ts` is a recording stand-in. It appends every argument array it is called with to `bd-stand-in/state/calls.jsonl` in the run's home, keeps the issues it created beside it, answers the four writes of the Beads routes in the shapes `bd` prints (from `scripts/hearth/bd-answers.ts`, the module the unit tests use), refuses what `bd` refuses (an unknown parent or id, a claim of a closed issue), makes a child under a parent with every label of the parent and none of its metadata, as `bd create --parent` does (`childOf`, `x1gs.5.8`), answers the queue's calls (`show` of one id or several, a label/metadata `update`, and the `list` shapes of `GET /queue` and `GET /eligibility`) through `scripts/scheduler/queue-fixture.ts`, answers `export` (`GET /beads/counts`) with its issues one line each, keeps what `comments add` writes and answers the two reads of a council's bead source (`--readonly show <id> --json` with the issue, `--readonly comments <id> --json` with the comments it kept for it, oldest first, in the shape `bd` lists them: `bdAnswers.listedComments`) for an issue it knows, answers any other `list` with `[]` and exits 2 for anything else. The hearth's council runs `bd` by name too, so a council run on a bead reaches the stand-in (`council-bead.spec.ts`, `send-to-council.spec.ts`), and when such a run completes the hearth posts its verdict to the bead with one `comments add` (so those specs leave a `review:` comment on their bead). Its issues live in `issues.json` and its comments in `comments.json` beside it, read and replaced only through `bd-stand-in-state.ts`, which retries the sharing errors Windows raises when another process has a file open (measured: most renames fail while a reader loops). `standInComments(id)` (`stand-in.ts`) runs the stand-in itself with the council's comments read and answers what it printed. `scripts/dashboard/stand-in-state.test.ts` runs the stand-in's source for the comments it keeps. Ids are `e2e-<n>`, a child's `<parent>.<n>`.
  - Global setup (`global-setup.ts`) compiles it to `bd-stand-in/bin/bd` (`bd.exe` on Windows) in the run's home with `bun build --compile`, and stops the run when the build fails or the program does not answer. It is compiled because a hearth runs `bd` by name with an argument array, and only a real program of that name receives the arguments as they were given. Teardown removes that directory first and on its own (it is about 115 MB and nothing holds it open).
  - Both servers are started by bun's absolute path with a PATH of their own (`standInEnvironment` in `servers.ts`). The hearth's holds the stand-in's directory and nothing else: it can run no other `bd`, and `gh` is not found either. That directory also holds a stand-in for `git` (`git-stand-in.ts`, built and checked by global setup the same way): it answers `git worktree list --porcelain -z` with the directory it runs in as the only worktree, and exits 1 for anything else. A council run on a bead asks for that listing whenever the checkout's repository has a linked worktree, which a developer's checkout has and CI's fresh clone does not; without the stand-in the listing failed and the council specs saw a "worktrees: not searched" line on such a machine only (x1gs.7.14). The real `git` is not used: it would search the developer's own worktrees. The dashboard's holds the stand-in's directory first, then node's (Vite's launcher needs it): a hearth the dashboard starts in place of the suite's inherits that and finds the stand-in. Playwright starts the servers before global setup; until the stand-in is built the hearth finds no `bd` at all.
  - At config load the suite refuses to start when node's directory, or a `node_modules/.bin` from the checkout up to the root of the drive (`bun run` puts those on the dashboard's PATH itself), holds a `bd` under any of its spellings. The message names the file. Run the suite with a node whose directory holds no `bd`.
  - A spec that writes calls `requireStandIn` first (`builders.spec.ts`): it reads `/queue` and requires the stand-in's own record to have grown by a `list` call. Every spec of a run shares that record, so compare it from a mark taken in the test and leave `list` calls out.
  - A test that acts on a bead creates it first through the page, so the stand-in knows it and each project's run has its own. The one exception is the queue state a test starts from: `seedProposed(id)` (`stand-in.ts`) writes `queue:proposed` and its `queue_state` metadata onto a bead the test created, through the shared state module, as the queue's `propose` would (`builders.spec.ts` uses it too, for a label that bd then prints with a claim). `workbench.spec.ts` writes other starting states the same way (`seedQueue`): a queue label with no `queue_state`, which the board's Propose takes in, and a bead paused while running, which no route can make without a shift. `standInCalls`, `requireStandIn` and `createFromBuilder` (with `createButton` and `createdId`) live in `stand-in.ts` too.
  - A spec that needs the page without a stream answers the stream route before a new document loads: navigating by hash keeps the stream an earlier page opened (`workbench.spec.ts` reloads after stubbing it). A snapshot is only read when the page loads: after `stubSnapshot`, load the page afresh (`openIssues`).
  - An answer the hearth would only give when `bd` misbehaves is served by the test with `page.route` (a `504` envelope, an aborted request): that request never reaches the hearth, so the stand-in's record must show no call for it. A write is held in flight with `holdPosts`; `release(answer)` answers it there (a `504` from `notFinished`) instead of letting it through. Every bead write the page has to report (an outcome not known, a refusal its view did not live to show) is drawn in one list on every route, `writesToCheck(page)` ("Writes to check"), not inside the actions block or under the builder: filter its notices by `hasText` (`claim on <id>`, `create "<title>"`), since several can be listed at once. Held until the page is gone (the reload test) it never reaches the hearth either; released (the sent-once test) it does, and the stand-in's record must then show exactly one call for it. Two presses in one turn of the event loop are made with `pressTwiceAtOnce`: a `dblclick` gives the page time to draw the button disabled and proves less.
- **The dashboard's rebuilds run a stand-in too.** The dashboard rebuilds the snapshot after every tracker write the hearth makes (and on a change under `.beads/`). In the suite, `DASHBOARD_BUILD_SCRIPT` points it at `build-stand-in.mjs`, which writes no snapshot, appends a line to `build-stand-in.log` in the run's home (`buildStandInRuns()` in `servers.ts` counts them) and exits 0. Every write a spec makes is therefore followed, about two seconds later, by the dashboard telling open pages the snapshot was rebuilt; a page then reads `data/beads.json` again in place (through a test's `page.route`, if it has one) and is not reloaded. `snapshot-rebuild.spec.ts` checks that: a title typed in the bead builder and not sent stays in place while another tab's write is rebuilt, the document is the same one, and the shell shows the snapshot the page read again.
- The issue views in a local run may be showing this checkout's own `docs/data/beads.json`. A rebuild never replaces it in a run (the stand-in writes nothing), but `bd` writes made elsewhere while the suite runs can still make the pages read it again. Leave Beads alone until the run ends.

## Notes

- Counts, as of the stream retry and lost specs, the Forge run gate history spec, the Commands page spec (its slash-command rows and, in a second test, its skill rows), the council bead preview spec, the stored council run spec, the send-to-council spec, the council stream deltas spec, the Workbench's propose and resume-from-running tests and its inherited-label test: 270 tests exist (135 per project). A normal run selects 249 (123 desktop, 126 mobile): the 18 captures are opt-in and the 3 mobile-only tests are left out of the desktop project; with `SHOT_DIR` set, `--list` shows 267. Recompute with `bun run verify:ui -- --list`, and with `SHOT_DIR` set to include the captures.
- What a green CI run does not prove. CI has no Beads snapshot and no forge run, so there: Dashboard, All issues, Epics and Insights render their "No snapshot loaded" state (the Dashboard below its two stat rows from the hearth), and the real-API Forge run test takes its no-run branch. Populated states are covered only where a test serves a fixture. CI runs Chromium on Linux only.
- A failed CI run uploads `test-results/` (a trace per failed test and a screenshot of the page at failure) as the `playwright-test-results` artifact. Open a trace with `bunx playwright show-trace <trace.zip>`.
- `bun run lint` does not cover this directory. Keep new files clean with `bunx biome check <file>`.
- `bun test` does not collect these specs (`bunfig.toml` roots it at `scripts/`).
