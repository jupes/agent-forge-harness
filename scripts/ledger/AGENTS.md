# AGENTS.md — scripts\ledger

Local agent guidance for this directory.

## Scope

- Applies to this directory and descendants unless a deeper `AGENTS.md` overrides it.
- Parent guidance still applies unless this file states a stricter override.

## Local Rules

- Keep edits focused on files within this subtree.
- Follow repository-level quality gates before shipping.
- `appendEvent` is the only writer of the `events` table. It never throws; emitters must not fail because the ledger could not be written.
- The ledger is metadata only. A new payload field needs an entry in `payload-allowlist.ts`. Every string `appendEvent` stores goes through the secret scanner (`scripts/secret-patterns.ts`), with two outcomes: payload strings and the executor's `provider`, `model`, `effort` and `smith` are stored redacted; `workspace`, `beadId`, `runId`, `sessionId` and a caller-supplied `ulid` are what events are joined on, so an event whose value the scanner would change is refused (`{ ok: false }`, nothing stored) rather than stored under a secret or a mangled id. `kind` and `ts` are validated, not scanned. The scanner only knows the shapes in its list, and leaves `sk-` alone inside an ordinary lowercase slug such as `task-queue-state-machine-v2` so ids like that stay queryable.
- The consequence of that refusal: a checkout whose path, or a bead, run or session whose id, the scanner flags gets no events at all, since every event that carries the value is refused. Ordinary names can be flagged: `sk-` after a single letter (a checkout directory named `ask-the-docs-…`) or after an uppercase one (a run `Task-queue-…`, or a POSIX checkout of that name; a Windows path is stored lowercased, which drops the capital). `refusedJoinValue` (`append.ts`) is that rule, workspace read as stored. The refusal is reported, not silent: `appendEvent` returns it with one stderr line, which a background hook's host does not show; `.claude/hooks/session.ts` prints a refused `session.started` and its reason on stdout, which the session reads; and `forge:audit` adds one stderr line when its scope (the checkout it runs from, or a `--bead`, `--run` or `--session` value) is such a value. Storing such a value marked instead of refusing it is an open decision, not taken here.
- `db.ts` imports `bun:sqlite`, which only loads under Bun. Nothing Vite loads under Node and nothing the dashboard bundles for the browser may import from this directory at runtime; `scripts/council/ledger-events.test.ts` walks both graphs with `scripts/import-graph.ts`, from `vite.dashboard.config.ts` and from the pages' module scripts (`docs/js/app.tsx`, `docs/js/council.tsx`). The walk is the rule; what it reaches today is, under Node: `scripts/hearth/vite-plugin.ts`, `supervisor.ts`, `lock.ts`, `home.ts`, `gate.ts`, `paths.ts` and `scripts/agent-forge-home.ts`; in the browser, outside `docs/js/`: `scripts/forge/runs.ts`, `phases.ts`, `review-rules.ts`, `scripts/council/discussion.ts`, `scripts/dashboard/forge-run-model.ts`, `scripts/hearth/paths.ts`, `validate.ts`, `scripts/scheduler/queue-table.ts`, `scripts/eval-verdict.ts`, `scripts/quality-gate-identity.ts`, `scripts/run-correlation.ts` and `types/hearth.ts`. The council service and workflow (`scripts/council/service.ts`, `workflow.ts`) run under Bun — in the CLI, the MCP server and the hearth — but still take the ledger by injection and import nothing from here.
- The directory the ledger lives in is resolved by `scripts/agent-forge-home.ts`, a leaf module the hearth shares (`scripts/hearth/home.ts`): the ledger owns `ledger.db` (and SQLite's `ledger.db-*` files), `backups/` and `hook-probe.jsonl` there; the hearth owns `hearth-<key>.lock` and `tokens/`.
- Tests must not write the real ledger under the user's home. Two things guard that: `test-preload.ts` points the test process (and any child that inherits its environment) at a temp `AGENT_FORGE_HOME`, and a test that hands a child its own environment must put a temp `AGENT_FORGE_HOME` in it — a scrubbed or allowlisted environment (the MCP stdio client builds one) drops the preload's setting and the child falls back to the OS home. `test-isolation.test.ts` checks the second rule only in part: it re-runs every test file that can start a process with the OS home pointed at a scratch directory and fails if `.agent-forge` appears there. It finds those files by a scan: a `*.test.ts` file under `scripts/` is in when it, or a module it loads (followed by `scripts/import-graph.ts`), names a spawn primitive (`Bun.spawn`, the Bun shell, `child_process`, the MCP stdio client), so a test that starts a hearth or an executor through a module is covered; a process started some other way is not. A child whose environment has neither `AGENT_FORGE_HOME` nor the OS home variable (`USERPROFILE` on Windows, `HOME` elsewhere) would take the OS home from the user's account and miss the scratch directory; the re-run catches it all the same when it is started with `Bun.spawn`, `Bun.spawnSync` or `node:child_process`, because the spawn probe gives it the scratch `.agent-forge` as its `AGENT_FORGE_HOME` (see `isolation-probe.ts` below). Its blind spots: such a child started through the Bun shell (`Bun.$` given an environment of its own; none today, bead `agent-forge-harness-usuz`) or by another child, which runs without the preload and so without the probe, writes the real ledger in the re-run as in an ordinary run and the scratch directory never sees it; and a test file under another name (`.test.tsx`, `.spec.ts`; none today) is not scanned. The guard's header lists the rest. A test that asserts on ledger contents creates its own temp ledger and passes its `path`.
- The quality gate (`.claude/hooks/quality-gate.ts`) appends `gate.ran` — and `verdict.bound` when its strict check bound a verdict — from the builders in `scripts/quality-gate-ledger.ts`. The bead and run on both come from the gate's run correlation (`scripts/run-correlation.ts`) or are absent; the environment and run state never name them. The gate runs the test suite, so a test may spawn it only where its own checks cannot run: `scripts/quality-gate-hook.test.ts` does, in a scratch directory that is not a repository and has no `package.json`, with a PATH that reaches no real `bun`, and no `git` that finds a repository: empty, or system directories only (where a system `git` is there, as on Linux, the scratch directory is not a repository to it), or (for two tests) stand-ins for `bun` and `git` in front of those.
- `verdict.bound` carries who judged only as a schema 2 verdict declares it: `evaluatorIdentity` is the typed evaluator, `evaluator` is the executor that was observed to run (never the requested one; absent for a human and when nothing was observed), and `verdictArtifact` is the file as read (path, SHA-256, size, schema version). A legacy schema 1 verdict yields neither evaluator field. The allow-list stores an `evaluatorIdentity` only when the verdict parser accepts it, and a `verdictArtifact` only with a real digest and size. A `verdict.bound` row is not by itself evidence of strict completion: `forge:review` emits one for a review round's verdict without enforcing the evaluator policy. Strict completion is a linked gate log entry whose `eval-verdict` check passed and which carries `evaluatorArtifact`.
- Schema changes are a new entry appended to `MIGRATIONS` in `db.ts`; existing entries are never edited.
- `resolveCheckout` (`workspace.ts`) spells a checkout by its real path on disk, so a Windows 8.3 short name or a link does not make one directory two workspaces. Emitters get `workspace` from it (through the hook context or `resolveAttach`); `appendEvent` and the query only normalise slashes and drive-letter case, so a `workspace` handed to them directly is stored as spelled.
- `hook-events.ts` is what the Claude Code hook scripts (`.claude/hooks/ledger-hook.ts`, `.claude/hooks/session.ts`) call. Its handlers take the parsed stdin object and injected dependencies, store names, hashes and sizes only, and never throw into the host. A hook event with no known model carries no `executor` — never a placeholder.
- `.claude/hooks/session.ts` takes its event from stdin `hook_event_name`, else from a `SessionStart` / `SessionEnd` token on its command line, else acts as SessionStart (a run by hand). The command-line token is what keeps a SessionEnd whose payload is missing or late from running the SessionStart path; the registration in `.claude/settings.json` does not pass the token yet, so until it does that case still falls through to SessionStart.
- The hook tests in `hooks.test.ts` spawn the real scripts with a from-scratch environment (temp `AGENT_FORGE_HOME`, temp `HOME`/`USERPROFILE`, an empty `PATH`), so no live session id leaks in and neither `bd` nor `git` can run. One test swaps the empty `PATH` for a directory whose only program is a recording `bd` (and passes `ComSpec` through, which a Windows child needs to start a shell): it reads back which `bd` commands a hook ran.
- No hook or script pushes the tracker, which is local-only. Two tests in `hooks.test.ts` hold that. The recording `bd` must see nothing from the ledger hook or from a session end named by its payload or on the command line, and nothing that pushes from a session end named by neither (which runs the SessionStart path, see above). And a read of `.claude/hooks`, `.claude/skills`, `.agents/skills`, `.github` and `scripts` (Markdown aside), the registered hook commands and the package scripts fails when the two words of that subcommand stand next to each other, even in a comment or a fixture: write "the tracker push" instead, and build a fixture from parts as the test does.

## Notes

- `bun test scripts/ledger` runs this directory's tests.
- `forge:audit` cuts a result at `--limit` (default 500) and says so in one stderr line, as it does when its scope is a value the ledger refuses (above); the `--json` envelope's `data` is always the array of events and never carries a note. The cut itself is `queryEventPage` in `query.ts`, shared with the hearth's `GET /events`, which also takes its filter rules from `parseAuditArgs`: a new `forge:audit` flag does not reach the API until it is added to the route's own list.
- `query.ts` also holds the reads the hearth serves: `listSessions` (bounded to the newest 50,000 events of a workspace; one pass, then lookups by primary key — a per-session `ORDER BY id DESC` makes SQLite walk the workspace index), `activeReservations` (through the kind index, for the same reason) and `latestEventId`.
- `fixtures/` holds scripts that tests and `bench.ts` spawn as child processes; they are not entry points.
- `isolation-probe.ts` covers a child the re-run in `test-isolation.test.ts` would not see by itself: one whose environment names neither `AGENT_FORGE_HOME` nor the OS home variable (`USERPROFILE` on Windows, `HOME` elsewhere) takes its home from the user's account, not from the scratch directory. Bun's spawn on Windows fills a missing `USERPROFILE` from the spawning process; a POSIX spawn (CI runs on Linux) fills nothing. For its re-run the guard sets `AGENT_FORGE_ISOLATION_HOME` to `<scratch>/.agent-forge`, and the preload then wraps `Bun.spawn`, `Bun.spawnSync` and the `node:child_process` functions in the test process so such a child is started with `AGENT_FORGE_HOME` set to that directory, where the guard looks. An ordinary test run installs nothing. Not wrapped: the Bun shell, and a process a child starts. The guard's test runs `fixtures/home-less-child.ts` (a test file not named `*.test.ts`, so the suite skips it) through the re-run to show such a child is caught; it starts its children only when its own home is a temp directory, and its emitter writes only there.
- `bun run scripts/ledger/bench.ts --hook 20` times the PostToolUse hook against a process that does nothing.
