# Owned interactive process supervision

Child `agent-forge-harness-cla5.4.2.4` adds an opt-in `stdinMode: "interactive"` overload to `supervise`. Existing serialized `stdin` and the legacy process lifecycle remain unchanged. This primitive is a trusted embedding API, never an HTTP command surface or execution authorization. The caller still checks scope, allowance, audit, private lease and original request identity before dispatch, filters the provider environment and owns the provider protocol.

`InteractiveSupervised.pid` is the owned bootstrap process tree root. `providerPid` resolves to the separate actual native program PID after its launch. A journal must keep these identities distinct. `write(string)` accepts ordered bounded input; it does not prove that the native program consumed it. Native matched protocol responses provide that evidence. `end()` sends EOF after earlier writes. `stop()` settles after the owned tree and readers stop.

## Startup ownership

Launching an unrestricted CLI and assigning it a Windows job afterwards leaves an early-helper race. Interactive supervision instead starts a fixed trusted bootstrap which runs no provider code before a private ownership grant. The supervisor establishes the mandatory kill-on-close job before writing that grant. Failed or throwing ownership setup kills the bootstrap and refuses without starting the actual CLI. The bootstrap is gated, not OS-suspended; the job constructor is shared with the existing suspended native-console primitive. Once granted, the native program and its immediate helpers inherit the owned job. Normal Windows completion terminates the held job handle, never an exited numeric PID. On POSIX the bootstrap leads the owned process group; descendants retain its group lifetime. A process deliberately leaving that POSIX group remains outside this guarantee.

Source startup invokes the native Bun executable with `--no-env-file`, `--no-install` and the fixed `interactive-bootstrap.bunfig.toml`. The bootstrap runs in a newly created empty OS temporary directory with isolated HOME, USERPROFILE, APPDATA and XDG directories, disabled transpiler caching and a minimal OS-only environment. Provider BUN_OPTIONS, NODE_OPTIONS, PATH, config and credentials are not inherited by the bootstrap. They cannot execute repository preloads before ownership. The actual caller-filtered provider environment, cwd and argv arrive only inside the bounded private grant after ownership; no grant content is written to stdout, stderr or the ledger. Empty private directories are removed after completion; unexpected files are preserved.

The desktop's compiled `hearth` supports the same internal `--interactive-bootstrap` mode. That branch imports neither the hearth server nor the Keeper reader. Normal compiled startup and the existing `--keeper-reader` branch retain their behavior. A trusted `bootstrapCommand` prefix supports packaged/fixture entry points; it is not a public launch field. `beforeStart` is a trusted ownership barrier before the provider grant; `interactiveGuard` is a trusted failure fixture only.

Attended shift capture always uses this owned mode. Its synchronous `holdTree` marks the private lease's obligation before the grant; the actual provider PID then crosses an awaited, bounded private `started` write. Only after that write commits does the adapter send its one prepared stdin body and EOF. Early stdout waits behind the same process-record/input barrier within a 256-frame/one-MiB bound. Prompt metadata is emitted only after that input write. `finish(exit)` follows held-tree cleanup and output drain. A private process-write deadline or Stop fences late work and sends no delayed input. Ordinary adapters without private capture retain serialized stdin and their existing lifecycle.

The implementation module has no entry side effects. Source supervision uses `interactive-bootstrap-entry.ts`; the compiled hearth calls the pure implementation explicitly. This avoids platform-dependent compiled `import.meta` entry detection executing the bootstrap twice.

The actual program inherits stdout/stderr directly. The trusted wrapper sends exactly one fixed actual-PID message over Bun's private JSON IPC channel, bound to that wrapper; it does not place controls on provider stdout. The actual program receives neither the IPC API nor its channel environment. After the actual program exits and input settles, the wrapper disconnects IPC and exits with that program's status. The parent then terminates its held group/job before awaiting stdout/stderr EOF, closing helpers which still hold inherited pipes. Buffered terminal bytes remain in the parent-facing kernel pipe rather than an intermediary reader; no drain timer discards them. Startup output arriving before the PID control is held within a 256-frame/one-MiB bound.

## Bounds and failure truth

The private grant is one UTF-8 frame of at most 128 KiB, read within five seconds. Provider input has a cumulative byte cap (one MiB by default, maximum sixteen), at most 256 pending frames and a write/EOF deadline (five seconds by default, maximum thirty). The separately bounded grant is additional to that provider budget. This cumulative cap remains in force after writes settle because Bun can acknowledge buffering before consumption. The bootstrap independently bounds input to sixteen MiB and its process lifetime to at most thirty minutes. The parent bounds inherited stdout to sixteen MiB and stderr to one MiB. The caller supplies tighter protocol line, stream and turn limits.

Any input refusal/deadline, output-reader failure or Stop closes the owned tree. Late input completion cannot reopen its pipe or grant. Windows job termination can report exit zero, so callers must retain an independent protocol/storage/input failure latch and require both a valid provider terminal result and process success. Exit code alone is insufficient.

Focused tests use actual inert native processes. They cover source and compiled entry points, a planted preload which runs without isolation, blocked pre-grant execution despite hostile config/environment, zero native dispatch when the owner is killed before the grant, and actual immediate-native-helper cleanup when the owner is killed after it. The compiled entry test also verifies the sealed Keeper reader against its hermetic hearth fixture. No live model, account, provider credential file or real tracker is used.

A compiled native normal-exit regression starts a helper inheriting stdout and stderr, writes a terminal line plus a buffered unterminated final frame, and exits zero. Both output frames and buffered stderr reach the caller; completion does not wait for the turn timeout, and the held ownership job removes the helper. This checks the runtime's observed pipe-close behavior rather than assuming that inherited pipes always close themselves.

The cache-disable value and `--no-env-file` behavior follow [Bun's environment documentation](https://bun.com/docs/runtime/environment-variables). Fixed JSON IPC and `process.send` follow [Bun's child-process documentation](https://bun.com/docs/runtime/child-process). CLI config flags and behavior are exercised with pinned Bun 1.4.2.
