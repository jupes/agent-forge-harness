# AGENTS.md — scripts/config

Layered config (`agent-forge.toml`) for smiths, benches, the executor env allowlist and the shift's defaults (`[shift]`).

- `load.ts` is the only reader; precedence and the never-inherit rule for `execution.env.pass` live there.
- The machine (user) file is `config.toml` in the Agent Forge home (`machineConfigFile`, through `scripts/agent-forge-home.ts`): `AGENT_FORGE_HOME`, else `~/.agent-forge`, read from the process environment as the OS home is. `LoadOptions.env` does not move it: `forge:exec` passes the environment it hands its child there. An explicit `home` (an OS-home stand-in) still wins. A file read from a moved home is still the user layer, so its `execution.env.pass` never applies once a workspace file exists.
- Parsing uses `Bun.TOML` (no dependency). It is lenient on some malformed input; validate shapes, not syntax.
- Keep provenance on every value — `forge:config show` is the audit surface.
- Smith/bench names and shapes come from `types/hearth.ts`; do not redefine them here.
- A name someone typed (a smith, a bench, a smith field, a `get` key) is looked up as an own key (`Object.hasOwn`): `constructor`, `__proto__` and `toString` are keys of every object, so a plain index reads them as present. A smith cannot be named after one: `loadConfig` refuses the table and `set` refuses the key.
- `write.ts` is the only writer (`forge:config set <key> <value> --user|--workspace`). It edits one line in place and keeps everything else: comments, order, a byte-order mark and CRLF line endings. It refuses any file with a line it does not fully read (a dotted key, an inline table, a multi-line string, `[[array]]`), and checks every edit twice before writing: the file must parse to what it held with only that key changed, and `loadConfig` must accept it (through `LoadOptions.contents`). Keep both checks: the deep compare is a second line of defence that no test reaches today.
- `keys` lists the keys `set` writes (`settableKeys`): every field of every loaded smith, not just the ones a file sets, and every `shift.<key>`. A `[shift]` number is typed as digits with an optional fraction and written bare; `for` is written quoted; the loader's check of the edited file refuses a value out of bounds. A new smith is added by hand, because provider, model and effort have to arrive together.
- Writing the workspace file for the first time stops the user file's `execution.env.pass` applying, so `set` refuses to do that as a side effect. Setting `execution.env.pass` itself is allowed, and says which user values it replaces.
- `[shift]` holds what `forge:shift run` takes for each flag it was not given, and the host threshold: `concurrency`, `for` (a duration as the CLI takes it: `90s`, `30m`, `2h`), `max_beads`, `max_usd`, `repairs` and `throttle` (a share from 0.1 to 1: 0.85 is 85%; below 0.1 a shift would find any working host too busy and admit nothing). `config.shift` names them as `ShiftOptions` does (`forMs`, `maxBeads`, `maxUsd`, `throttle`); provenance reports each as `shift.<key>`, the duration as written. A key is set in either file and the workspace file wins a key both set; an unknown key, a `[shift]` that is not a table, or a value outside the shift's own bounds fails the load naming the file and the key, so every reader reports it, as for any other section.
  - What that stops: every config reader, not only the shift. `forge:config show`/`get`/`keys`, every `forge:exec` (each run of a running shift too), `forge:doctor --task`, the phase gate's executor flags, the auto loop, `eval-verdict`, and the hearth's `GET /config`, `GET /smiths` and `POST /queue/:id/reassign`. A file broken by hand during a shift makes each of its later runs refuse before the provider starts: the shift releases those beads to `queued` unrun and ends `drained`. Fix the file (the error names it and the key; `forge:config set` refuses a bad value before writing, so it can also repair one), check the beads it let go are `queued` (`forge:queue`), and start a new shift.
  - One place each: the builtins are `BUILTIN_SHIFT` in `defaults.ts`, written as a file writes them; the bounds are `SHIFT_LIMITS`, `SHIFT_MAX_USD` and `SHIFT_THROTTLE` there, checked by `wholeNumberError` / `maxUsdError` / `shiftLength` in `load.ts`, which `shiftOptions` and `forge:shift run --for` (`scripts/scheduler/`) call too; `parseDuration` is the pure `duration.ts` function re-exported here. `SHIFT_DEFAULTS` and the host sampler's `DEFAULT_HOST_THRESHOLD` read the builtins; do not write a default or a bound of the shift's in code anywhere else.
  - No `[shift]` key is a security key. A workspace file inherits the user file's `[shift]` (a key it does not set itself applies), `max_usd` included: both files are the operator's own and local (`agent-forge.toml` is gitignored), and a flag or `POST /shifts` may set any value up to the same bound anyway. The ceiling no layer can raise is the shift's own bound (`SHIFT_MAX_USD`, 1000), checked on every layer and every flag. Only `execution.env.pass` is never inherited.
  - The shift reads the config of the checkout it runs in (`runShift` loads it as each run's `forge:exec` does: that root, the exec home and env), while `forge:config` reads this harness's. They are the same file when the shift runs from this checkout, as `bun run forge:shift` and the hearth's `POST /shifts` do.
- The write replaces the file through a rename: a config file that is a symlink becomes a regular file, and its permission bits are those a new file gets. Edit a symlinked config by hand.
