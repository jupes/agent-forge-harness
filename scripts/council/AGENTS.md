# AGENTS.md — scripts\council

Local agent guidance for this directory.

## Scope

- Applies to this directory and descendants unless a deeper `AGENTS.md` overrides it.
- Parent guidance still applies unless this file states a stricter override.

## Local Rules

- Keep edits focused on files within this subtree.
- Follow repository-level quality gates before shipping.
- `service.ts`, `workflow.ts` and `ledger-events.ts` never import `scripts/ledger/` or `ledger-wiring.ts`, statically or dynamically: a run reaches the ledger only through the functions its caller hands it. `ledger-events.test.ts` walks the import graph to hold that, and holds the same for what Vite loads under Node (`vite.dashboard.config.ts` and the hearth plugin it imports — the SQLite driver does not exist there) and for what the dashboard bundles for the browser (`discussion.ts`).
- A council run records `council.run.started` and `council.run.finished` only when the caller injects `appendEvent` and an attach (`executeCouncilReview`) or `appendEvent` and `resolveAttach` (the CLI io, the service options). `ledger-wiring.ts` supplies the real ones, and only `cli.ts`, `mcp.ts` and the hearth's `server.ts` load it, each through a dynamic import where it runs as a command. Runs started from the dashboard go through the hearth (`scripts/hearth/server.ts`, a Bun process the dashboard proxies to): its `main()` hands the service `operatorCouncilLedger()`, which attributes a run to the workspace and the bead the request named and to no session, because the operator started it. A hearth built without that option records nothing, which is every test except the ones that ask `scripts/hearth/testing.ts` for a council ledger (that helper imports the wiring too, and points it at the test's own ledger).
- A bead source (`bead-source.ts`) packs one bead, the one its caller names in full, and nothing implicitly: `bd` is run only as `bd --readonly show <id> --json` and `bd --readonly comments <id> --json`, after `parseBeadsIssueId` has accepted the id and never before; the issue `bd` answers with must carry that exact id, and a comment row must name that bead. Of a dependency only the id and type are packed. The PR packer is called with `linkedCriteria: false`, so the beads a PR body names are not read. No code path writes to the tracker.
- A pr source reads no bead either, unless the operator asks (`x1gs.7.4`). `compilePullRequest` looks up the acceptance criteria of the beads a PR body names only with `linkedCriteria: true`, with `bd --readonly show`, and names the beads it packed in `metadata.linkedCriteriaIds`, which `contextListing` turns into a `linked acceptance criteria sent: …` line. Only the CLI asks, on `--linked-criteria`, which it takes with the `pr` command alone and which makes a real run print the listing on stderr first, as for a bead. Do not add the option to the service input, the MCP tools or the hearth route: there the run starts before anyone has seen the listing, and a PR body is written by whoever opened the PR.
- What a bead source may pack is a fixed list: id, title, type, priority, status, labels, dependency ids and types, acceptance criteria, each comment's timestamp and text, description, design and notes. Never owner, assignee, author or any other field; `external_ref` and `spec_id` are read only to find a pull request URL or a linked path. Adding a field is a decision for the owner, recorded on the bead.
- Scan first, derive second. `compileBead` scans every field it reads (`scanNamed`), whole, before it cuts a label, takes a path or a URL out of the text, reads a file or fetches a pull request; a field that is read but not packed is scanned too. `buildContextPackFromParts` then scans everything that will be sent as one text, in the order it is sent and again in reverse (a key can be written across two comments either way round; the closer passes that name or redact a hit run only when the first one finds something), and every label as written and as it will be shown (after control and invisible formatting characters are replaced) at once — all before anything is cut. A title or a label is likewise scanned in its one-line form before it is shortened. Scanning only one of the two forms was tried both ways and each let something through, and so did scanning them one after the other: a key written against a provider variable name, an invisible character beside the sign, is taken with the name by the first scan and the second then sees no assignment. So shown text goes through `scanShown` / `redactShown` (`context.ts`): the two forms have the same length character for character, `secretSpans` (`scripts/secret-patterns.ts`) says where each finds something, and the union is replaced; the two scans of what is left still follow. A hit names where it was, never the match.
- A cut can make a key where the whole text holds none: an ordinary slug (`task-queue-state-machine-…`) cut just after a hyphen twenty characters past its `sk-`. A bead's title (300 characters) and labels (80) are cut by `cutWhole`: when the cut form holds a find the whole one does not, the cut is made at the last whitespace before the limit, else a character at a time shorter until nothing is found. Never slice, lower-case or re-encode text before it has been scanned, and never echo text that was not scanned: a run-state path that is not a linked path is not shown at all.
- The budget is spent in part order — acceptance criteria, latest comments newest first, description, linked plan/research/report, pull request — in two passes: each part first takes what it needs up to its ceiling (description a tenth, each linked file 15%, the others none), then what is left goes back to the parts that were cut. So the criteria and the comments never lose bytes to a later part, while a long description or plan can be held to its ceiling and the pull request still packed. The sum of evidence bytes never exceeds `maxBytes`.
- A linked file is read only when its path, and the real path it resolves to, is a Markdown file under `plans/research/`, `plans/drafts/`, `plans/committed/`, `docs/plans/` or directly inside `reports/`, is at most 2 MB, and has no `council-runs` directory (in any letter case) in its path: council reports embed the evidence of earlier runs. One real file is packed once, whatever spellings name it.
- A pull request is fetched only when the parsed mention is `https://<origin host>/<origin owner>/<origin repo>/pull/<n>` with no userinfo and no port other than the default, and `gh` is handed a URL rebuilt from the origin and the number; what `gh` answers with must be that pull request. The origin remote's text is parsed and then dropped: it never appears in a listing line, an error, a title or metadata.
- What an operator is shown carries no control or invisible formatting character: `buildContextPackFromParts` replaces them in the source name, titles and listing lines, and `safeCommandError` in a failed command's stderr; both read the text as written and as shown at once (`redactShown`), scan what is left again after replacing, and cut last.
- A comment is packed as its timestamp on one line and its text quoted (`> `) below, whatever character ends its lines, so text inside a comment cannot pass for another comment's header.
- The listing (`source.metadata.parts`, `contextListing`) has one line per part considered and is what an operator sees before a provider is called: the CLI prints it (dry run, and stderr before a real bead run or a real pr run with `--linked-criteria`) and the engine's `run.started` event carries it for `council_status`. On the job path that is an event to poll: `council_start` returns before the bead has been read. Before a run, the service's `preview` packs the source exactly as a job does (the same checks, the same `pack`) and answers the listing and the pack's summary, never the evidence, with no run reserved, no model called and nothing recorded; the hearth serves it as the action `POST /council/preview`, and the dashboard's Council page offers to send a bead only once it has shown a preview of that very draft (`docs/js/council-preview.ts`). The listing is not rendered into prompts.
- Tests for a bead source hand in a fake command runner (`runner` on `prepareCouncilContext`, `runCommand` on the CLI io and on the service options, which the MCP options extend) or a stand-in service (`service` on the MCP options); a hearth test sets `h.commands.answer` on the test hearth, whose council runner refuses anything not arranged. No test runs the real `bd`, `git remote` or `gh`, and fixtures are invented, never copied from the tracker.
- On the job path the bead under review is the bead the run is recorded against. `assertCouncilInput` is the one check every host shares (the service's `start`, and the hearth's council route before it writes its audit row): for a bead source it requires `source` to be a Beads issue id and refuses a `beadId` that is not that id, so no request can have one bead packed and another credited; `start` reads each field of the caller's object once (`councilInputFrom`) and hands the copy to `begin`, which checks it and queues the job, so the job uses what was checked and never sees the caller's object. The copy is typed with every field of `CouncilServiceInput` required (present, possibly undefined), so a field added to the input and not to the copy fails to compile. `councilBeadId` then names the bead for the ledger, the caller's or else the source bead; the service's attach and the hearth's audit row both use it. The service's `start` and the hearth route check the kind nowhere else, so a kind added in `assertCouncilInput` is accepted by both: decide there what it means for `beadId`. The `sourceType` type and the MCP tool's schema and mapping name the kinds too.
- Untrusted text reaches a prompt only between tags from the prompt's one `promptFence` (`prompt-fence.ts`): each tag name ends in a token drawn for that prompt that none of the wrapped text holds, in any letter case or spacing, and the evidence preface states that rule. Draw the fence from every block the prompt wraps (`contextPromptData` for the evidence, the `promptJson` text of each JSON block) and hand it to `renderContextForPrompt`. JSON blocks go through `promptJson`, which writes `<`, `>` and `&` as escapes. Never write a wrapper tag by hand or escape the reviewed text itself: it is sent as written, line-numbered. `safety.test.ts` holds this over generated hostile text.
- The finished event is appended from a `finally`, so every started event gets one. The ledger stores the outcome, the cost and the chair's summary — never seat outputs, findings or the reviewed text. `--dry-run` creates no run and records nothing.
