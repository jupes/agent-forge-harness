## Notes

- `use-stream.test.ts` covers the dashboard's stream client: the state rules of `docs/js/app-state.ts`, the client of `docs/js/use-stream.ts` on a stand-in transport with stand-in timers (nothing in it waits on the real clock), the fetch transport on a stand-in `fetch`, and three tests against a real hearth (`startTestHearth`) for what a stand-in cannot show: that a resume carries the last id and the server then sends no second snapshot, that the sessions and reservations folded from events equal what the hearth's own routes answer, and that a route which is not a stream turns live updates off after one request. Two more run the real fetch transport, with stand-in timers, against a stand-in hearth on a loopback port that hangs: one accepts connections and never answers, and the other answers each stream with a snapshot and then goes silent. Three more run a view's reads (`readOperatorRoute`, `fetchDevApi`), with stand-in timers, against a stand-in on a loopback port that never answers, or sends its headers and never ends the body: each read fails at `READ_TIMEOUT_MS`. The reads of a static copy are shown with the switch on (`staticCopy: true`): nothing is asked for. Hooks are not run here (there is no DOM); the logic they call is in `createStreamClient`, `createRefetcher` and `startLiveRead`, which are. The page itself is exercised in `tests/e2e/live-stream.spec.ts`.
- Do not use bun's fake timers for these tests: the per-test timeout is faked with them. Pass a `Timers` stand-in to the client instead.
- `rebuild-pages.test.ts` runs a real Vite dev server with `rebuildPagesPlugin` and a stand-in build (a small script that waits for the test to write a `release` file), never `scripts/build-pages.ts` or bd. A build that blocked the server's thread could never be released, which is what those tests detect. Give each server a port the system just handed out (`freePort`), not port 0: Vite reads 0 as 5173 or the next free one, a range other dev servers on this machine use.
- `POST /__agent-forge/rebuild-pages` is answered only for a loopback peer (`isLoopbackAddress` from `scripts/hearth/gate.ts`, the check `guardRequest` uses) whose request passes the hearth's front door (`passesFrontDoor`, same module: `Host`, `Origin` and `Sec-Fetch-Site` each sent at most once, a loopback `Host`, an `Origin` when sent equal to that host's origin, `Sec-Fetch-Site` when sent `same-origin` or `none`), before the method is looked at: the hearth's guard does not cover it, because Vite answers it without the proxy. A request with neither `Origin` nor `Sec-Fetch-Site` (a terminal's, a test's `fetch`) passes, as at the hearth. Reuse those functions; do not copy the rules here. Its test sends a real request from source address `127.0.0.2` through a Node child process (Bun ignores `localAddress`), which the check counts as another machine; it is skipped where `node` is not on PATH.
- The snapshot is rebuilt after a tracker write in two ways: the `.beads/` watcher (which sees nothing in a linked worktree, where bd writes the main checkout's tracker), and `api.rebuildSoon`, which `vite.dashboard.config.ts` hands to `hearthPlugin` as `onTrackerWrite` (see `scripts/hearth/AGENTS.md`). Both share one 700 ms debounce. A write made with `bd` outside the hearth is seen by neither in a worktree; Refresh snapshot reads the live tracker. The tests mount both plugins wired that way against `startTestHearth` (fake bd); the config file itself is not loaded by a test.
- A rebuild the server started itself (first build, watcher, `rebuildSoon`) that succeeded is announced with `SNAPSHOT_REBUILT_EVENT` (`snapshot-events.ts`, constants only, also bundled for the page) over Vite's HMR socket, never with `full-reload`: a reload discarded unsaved input on every open page. `docs/js/use-snapshot-rebuilt.ts` reads `data/beads.json` again in `app.tsx` and `use-shell-chrome.ts`, and keeps what the page shows when that read fails. The Refresh snapshot POST still answers only the page that sent it. The unit tests record HMR pushes and assert the event and no `full-reload`; `tests/e2e/snapshot-rebuild.spec.ts` checks the page.
- `DASHBOARD_BUILD_SCRIPT` (read by `vite.dashboard.config.ts`) runs that script with the dev server's runtime in place of `scripts/build-pages.ts`. The browser suite sets it to its stand-in, which writes no snapshot.
