# AGENTS.md — scripts\hearth

The hearth: the standalone loopback control-plane server (`bun run hearth`), its Vite integration, and the MCP server that is its client (`bun run hearth:mcp`).

## Scope

- Applies to this directory and descendants unless a deeper `AGENTS.md` overrides it.
- Parent guidance still applies unless this file states a stricter override.

## Local Rules

- Every request passes `gate.ts` (`frontDoorOrigin`) before routing: loopback peer; `Host`, `Origin` and `Sec-Fetch-Site` each sent at most once (counted in `rawHeaders`); loopback `Host`; `Origin`, when sent, equal to the host origin; `Sec-Fetch-Site`, when sent, `same-origin` or `none`. Do not add a route that skips it.
- The operator API is one table: `api.ts` is the runner; `routes/operator.ts` assembles the table and holds the actions and the stream row; `routes/operator-reads.ts` holds the read rows; `routes/beads.ts` holds the tracker writes and the options row; `routes/queue.ts` holds the queue actions; `routes/shifts.ts` holds the shift rows. A new route is a new row. Never check the origin, the token or the audit row inside a row, and never answer JSON from one: the runner does all of it, for every row, in one order (same-origin, token, body, validation, `operator.action`, effect).
- Every mutation is an action row. `routes/council.ts` and `routes/dev-api.ts` only read; do not add a POST branch to either. Their tests mount them on their own `node:http` server; an action row is tested through a hearth (`testing.ts` gives a hermetic one), and `api.test.ts` iterates the table: a row with no fixture there fails the suite.
- Handlers in `routes/` keep the `(req, res, next)` shape and the `{ ok, data, error }` envelope.
- State lives in `AGENT_FORGE_HOME` (default `~/.agent-forge`): `hearth-<hash(root)>.lock` and `tokens/<hash(root)>.token`. Tests must pass a temp `home`; never touch the real one. The event ledger lives in the same directory (`ledger.db`, `backups/`, `hook-probe.jsonl`); `scripts/agent-forge-home.ts` resolves it for both, and an `AGENT_FORGE_HOME` that is empty or only whitespace counts as unset.
- `vite-plugin.ts` and what it imports (`supervisor.ts`, `lock.ts`, `home.ts`, `gate.ts`, `paths.ts`, `loopback.ts`, `follow-tracker-writes.ts`) are loaded by Vite under Node: no `bun:` module and nothing from `scripts/ledger/` there. `server.ts`, `api.ts`, `stream.ts` and `routes/` run only under Bun, and `server.ts` and the two `routes/operator*.ts` modules import the ledger. `paths.ts` is also bundled for the browser (`docs/js/operator.ts`): constants only.
- A council run's event stream (`GET /council-api/runs/:id/events`, `routes/council.ts`) sends the whole job as a `snapshot` on every update, unless the client asks with `?deltas=1`: then the whole job once and after it `delta` messages with only what changed since the job that client was last sent (`scripts/council/job-delta.ts`: the events and discussion rounds appended, and the other fields that changed or went away), or a `snapshot` again for an update that is not that job plus appended entries. `applyCouncilJobDelta` rebuilds each job a snapshot client is sent. The dashboard's council page does not ask for deltas yet (`agent-forge-harness-bj90`).
- Council runs started through the hearth are recorded only when `createHearth` is handed `councilLedger`. `main()` hands it `operatorCouncilLedger()` (loaded by a dynamic import); a test hearth is handed none and records nothing unless the test asks `testing.ts` for one (`councilRuns`). That builder attributes a run to the workspace and the bead the request named and infers nothing: the operator started it, not the agent session whose mirror file is in the checkout. A request whose source is a bead names that bead: the council route takes the bead for its audit row and for the service from `councilBeadId`, after `assertCouncilInput` has refused a `beadId` that is not exactly that id.
- A hearth serves exactly one root. A dashboard reuses a live hearth only when the lock's root matches.
- The token is minted at start and enforced by the runner on every action row. It is honoured only while the file the lock names still holds it; the token route answers 503 whenever no token could be honoured.
- `createHearth` listens, takes the lock and writes the token file as one step. When any of it throws, a lock this start took is released and the table, the council service and the server are closed before the error is rethrown: nothing of a failed start keeps answering.
- The hearth's appender (audit rows, and the outcomes the rows record) opens the ledger with no wait on another connection's lock (`LEDGER_FIRST_OPEN_WAIT_MS`); the runner's three attempts are the wait, so an action on a locked ledger is 503 in under a second whether or not the hearth had opened the file, and the serving thread is free between attempts. The read rows and the stream still open it with the ledger's own 2 s wait.
- Under Bun's `node:http`: a header sent twice arrives as its last value (only `rawHeaders` shows the repeat, which is why the runner counts there); a client that disconnects closes the request and the socket but not the response (which is why `stream.ts` and the council run stream in `routes/council.ts` listen to all three); response headers are not sent until the first write unless `flushHeaders()` is called; `res.write` returns true however much is waiting, so `res.writableLength` is what `stream.ts` reads for backpressure; `drain` can fire inside a `write`, before the caller's next line, so the stream's pump refuses to be re-entered; ending a response to a client that is not reading frees nothing until that client leaves, so a stalled stream's socket is destroyed instead; and leaving `for await (const chunk of req)` early makes the runtime end the response itself with an empty 200, so the runner's body reader (`requestBody` in `api.ts`) reads with listeners, takes them off when it stops, and pauses a body that has not ended.
- An action's body is read under a time limit (`BODY_TIMEOUT_MS`, 10 s; a test passes `api.bodyTimeoutMs`). A body that has not ended by then is answered 408, or with the refusal the request already had, and its connection is closed once the answer is written. A refusal given before the body is read (the origin, the token, a declared length over the cap) is sent once the body has been read and dropped: under Bun an answer sent while a `Connection: close` client was still writing a body of 2 MB or more was not received at all (measured on Windows; 256 kB was). A refusal whose body has not begun to arrive within 50 ms (`HELD_BODY_MS`) is sent at once, as for a client that holds its body back until it has heard nothing (the MCP server, below); the body is read and dropped after it, and the connection closed at the time limit if it never ends. Accepted, not handled: such a client that waits longer than that and then sends a large body with `Connection: close` can still lose the refusal; and an answer outside the table (the front door's 403, a 400 for the path, a 404 or 405, the token and health routes) is sent without reading the body, so the same kind of client can lose it, and a body there that never ends holds its connection until the client leaves.
- `bd` is never run synchronously here. `bdRunner` is asynchronous, takes an argument array and no shell, and never rejects: an argument the runtime will not pass on (one holding a NUL, a command line past the platform's limit) makes `execFile` throw before anything starts, and the runner resolves that with no exit status and a reason of its own, which names the runtime's error code when there is one and never the arguments (the runtime's own message for a NUL repeats the argument). Nothing is sent on the child's standard input, and the runner ends it at once: a `bd` that reads it (`create --description=-`) reads nothing and goes on, instead of waiting for the runner's limit. Its tests start `process.execPath` as a stand-in, never `bd`. The checkpoint review refuses a note holding a NUL before anything is recorded; its note limit keeps the comment far under a command line's. The queue read is always the same argument array (`QUEUE_LIST_ARGS`), one at a time, with its own 15 s limit passed to the runner; every other call has the runner's 30 s. The council service is the one other thing here that starts `bd`: for a bead source it runs `bd --readonly show` and `bd --readonly comments`, and for a `pr` source `bd show <id> --json` for each bead the pull request's description names, through the council's own runner (asynchronous, an argument array, no shell, 30 s). `createHearth` wraps that runner in `hearthCouncilRunner`: `bd` runs in the checkout that holds the tracker (`localStateRoot`, as the hearth's own `bd` does), `git` and `gh` in the hearth's root. The `runBd` a test hands the API does not reach the council: `councilRunCommand` does, and `testing.ts` always hands one in, a recorder (`h.commands`) that refuses whatever its test did not arrange, so no hearth test starts a real `bd`, `git` or `gh` through the council.
- A write to the tracker (`routes/beads.ts`) is one `bd` call, never repeated, never with `--repo`. Build its arguments so that nothing a caller sent can be read as an option: every value as `--flag=value`, every positional after `--` (`bd comments add <id> --help` prints help, exits 0 and adds nothing), an id always present (`bd close` with none closes the last touched issue) and checked with `parseBeadsIssueId`. A description of exactly `-` is refused: `bd` reads it from standard input, which `bdRunner` ends at once, so the issue would be made with no description.
- `tracker-write.ts` is what every write to the tracker shares (the bead-id check, reading what `bd` printed, its refusal line, the never-started test, storing the outcome event). It has no runtime import from `routes/`, so `scripts/scheduler/queue.ts` uses it without loading the read rows. Keep it that way.
- The queue rows (`routes/queue.ts`: `POST /queue/:id/approve|queue|pause|resume|reassign`) are a way in to `scripts/scheduler/queue.ts` as the operator, and nothing more: the table of legal moves, the lock, the `bd` calls and the `bead.transitioned` event are there (see `scripts/scheduler/AGENTS.md`). Never write a queue label from a row. The moves take an empty body; `reassign` takes `{ smith }`, checked against the configured smiths in the validator, before the audit row, whose `target` is then the smith and whose bead is the bead. A row answers `404` for an id no bead has, `409` when the table refused, the bead is in no state, the lock was busy or another writer's label was found on the bead, `502` when `bd` refused, `504` when the outcome is not known, and never `403`. The scheduler's moves (`start`, `submit`, …) and `propose` have no row. The lock file is `queue-lock.db` in the hearth's home.
- The shift rows (`routes/shifts.ts`) are a way in to `scripts/scheduler/shift-store.ts`, the functions `forge:shift list` and `forge:shift stop` call, over `<home>/shifts`: a shift given another home is neither listed nor stopped here. `GET /shifts` lists the records of this hearth's workspace. `POST /shifts/:id/stop` takes an empty body and writes the stop request; the shift itself stops its runs, gives their beads back and records `shift.stopped`, so the row's only ledger row is its audit row. `404` for no such shift or another workspace's, `409` for one that has stopped. Starting a shift (`POST /shifts`) is not mounted.
- `GET /queue` marks each entry `backed`: whether the issue's own `queue_state` metadata names the entry's state, which is how the queue's own labels are told from one a child inherited. It also carries the bead's `smith` metadata and, for a paused entry, `resume` (its `queue_resume`, when that is a state it can return to).
- `GET /eligibility` answers `readEligibility` (`scripts/scheduler/eligibility.ts`) for the hearth's root: which queued beads may start and why the others wait. Three `bd` calls a read, coalesced; `502` when `bd` fails; not a stream collection.
- `GET /beads/counts` answers the dashboard's four Beads cards (`BeadCounts`): one `bd export` (`BEAD_COUNT_ARGS`, always the same array), counted by the snapshot builder's own rules (`scripts/beads-dashboard.ts`), so a card means what it meant when drawn from a snapshot. Coalesced like the queue read, with the runner's 30 s; `502` when `bd` fails; not a stream collection: the call prints the whole tracker (measured: about 2 MB and 1.3 to 2.7 s for 767 issues), so it is made when a page asks.
- `GET /scoreboard` answers `readScoreboard` (`scripts/ledger/scoreboard.ts`) for the hearth's workspace, the function `forge:audit --scoreboard` prints; its one parameter, `since`, is judged by `parseAuditArgs`. `routes/scoreboard.test.ts` compares the route with the CLI run as a child from the hearth's checkout. Not a stream collection, and no MCP tool reads it yet.
- Exit 0 from `bd` is not success. Confirm a write by what `bd` printed, take the id it printed as the bead that was written, and only then append `bead.transitioned`. Answer `502` when `bd` refused, with its error line and not everything it printed: before it refuses, `bd` can print a warning that repeats the title it was given; with `--json` some commands print the error on stdout; and the runner's `Command failed: bd …` line on stderr repeats every argument, so never pass that on. Answer `504` when the outcome is not known (a killed `bd create` still creates the issue), and for a create whose printed description is not the one that was sent (none when none was): `bd` made that issue, so the answer names it, and the page does not invite a second create after a `504`. Answer `409` for a close or a claim that changed nothing (`bd` exits 0 for an issue that was already closed, or already claimed by the same actor, and the time it prints is then from before the call began), and never `403` from an effect: the page posts an action again after a 403. Two seconds are allowed for the second `bd` rounds to, and they are a window, not a proof: a close repeated with the same reason inside them is answered and recorded as a close, and so is a claim made within two seconds of the issue's last change (the claim before it, or an edit), because the time read for a claim is `updated_at`, which any change moves. Do not read `started_at` instead: `bd` writes it only while it is empty, so a bead released and claimed again prints the time of its first claim, and that claim, which did change the bead, would be answered `409`.
- A call with no exit status is "`bd` could not be started, nothing was changed" only when stdout is empty and stderr is, whole and alone, the runtime's own message that there is no such program. Never decide it by searching stderr for a word: a `bd` that started prints warnings of its own, and a warning can hold any word, the title it was given included. Everything else with no exit status is a `504` that says the call was stopped before it answered or never started, and not which: a call killed at the runner's limit and one the runtime could not spawn for another reason (its working directory gone, which Bun reports as `ENOENT: no such file or directory, uv_spawn 'bd'`) look alike there.
- `bd-answers.ts` is what `bd` prints for a write, in one place: `testing.ts`, the browser suite's stand-in and the route tests all build their answers from it. Change it there, and check a change against a real `bd`.
- Under Vite the peer is always the dev server, so the loopback check for proxied traffic is `guardRequest` in `vite-plugin.ts`. Keep it failing closed.
- Vite's proxy ends the client's response only when the hearth's answer ends cleanly. When the hearth's socket closes mid-answer (a killed hearth), it left the client's response open, and a page's event stream heard nothing until its 45 s silence limit. `closeWithUpstream` in `vite-plugin.ts` destroys the client's response then. It tells a cut-off answer by `readableEnded` at `close`, not by `complete`, which Bun has already set to true there. `vite-plugin.test.ts` shows it with the page's stream client and a TCP relay between the proxy and the hearth whose connections the test cuts.
- Spawn the hearth as `bun scripts/hearth/server.ts`, never through `bun run`, so the pid in the lock is the server's.
- Under Bun, `fetch` and `node:http` send a request for `127.0.0.1` to `HTTP_PROXY` (or `http_proxy`) when the process started with one and no `NO_PROXY` entry is `127.0.0.1` or `*`, and nothing done at run time turns that off; `loopbackProxyVariable` (`loopback.ts`) holds the measured rule. So every client of a hearth here (the MCP server, the health probe, the tracker-write follower) uses `loopbackExchange`, and a new one must too. The hearth's own tests use `fetch`: `bun test` refuses to start in such an environment and says what to set (`test-preload.ts`, first in `bunfig.toml`'s preload list). Node goes direct unless `NODE_USE_ENV_PROXY` is on; the browser suite's global setup refuses that case.
- `hearthPlugin`'s `onTrackerWrite` is how the dashboard learns that the tracker changed: `follow-tracker-writes.ts` polls `GET /events?kind=bead.transitioned` on the hearth (over `loopbackExchange`, with the hearth's own `Origin`) once a second, one poll at a time, and calls it once per poll that found new events. The first poll only takes the newest id as its cursor; a failed poll keeps the cursor, so a write made while the hearth was unreachable is still found. It stops when the dev server's HTTP server closes. It sees only writes that append `bead.transitioned` (the Beads and queue rows), never a write made with `bd` outside the hearth.

## The MCP server (`mcp.ts`, `bun run hearth:mcp`)

- It is a client of the running hearth and nothing more. A tool is a row of `FORGE_TOOLS` naming a mounted route; a call is one request to it and the route's envelope is the result, as one text item. Never answer for a route there, read the ledger or run `bd`; never start a hearth from it.
- A tool is added with its route, as a row: `authority` is `operator` exactly when the route is an action row, and `scope` is `checkout` when the route reads the hearth's own root (run state, config files, the council's directory) and `workspace` when it reads the ledger or Beads. `mcp.test.ts` iterates the table against a real hearth: a governed row needs an entry in `OPERATOR_FIXTURES`, an agent row one in `READS`, every row one in `SCOPE_FIXTURES`, or the suite fails. The refusal matrix needs nothing per tool.
- Order of a call, and it is not to be rearranged: the name; the authority rule (a governed row in a session without `--operator` is refused before its arguments are looked at); the arguments; the request; the hearth; the token; one request. `tools/list` and `initialize` are the same for every session.
- The token is read for one governed call, from the path this module computes for the verified hearth (never a path taken from a lock), must be what `createToken` writes, is sent on that request only and is kept nowhere. An agent session has no function that reads a token file. Never put the token, a header value or a byte of an answer in an error message.
- Requests go through `loopbackExchange`, a `node:net` socket to `127.0.0.1`, never `fetch` or `node:http`: under Bun both send a loopback request to `HTTP_PROXY` when the process started with one, and no request option or change at run time turns that off. The query is built by `URLSearchParams`; a path parameter must match `SEGMENT`; a request target is at most `MAX_TARGET_BYTES`. A governed row carries its route's `maxBodyBytes` (the table test compares the two) and a larger body is refused here, where the reason can be given without sending the body. The exchange holds a body over 64 kB back for 100 ms after the head, so a refusal the hearth gives on the head alone (a token it does not honour) arrives before the body is sent: the hearth sends such a refusal at once when no byte of the body has come within 50 ms. A hearth slower than that reads the body and drops it before it refuses (the body rules above), and an accepted large request takes 100 ms longer.
- A lock is used only after its file name, token file, port and pid check out and its port answers the health route with that pid and that exact root; locks are found by reading the home and comparing real paths (`realpathSync.native`), so another spelling of a checkout is the same checkout. Two live hearths for one directory: the lock that comes first by name is used. These checks tell a stale lock or a reused port from a live hearth. They are not proof against a process of the same user that takes a dead hearth's port and answers the health route with the lock's pid and root: the pid and the root are not secrets (`x1gs.3.19`).
- The council's tools are re-exported through a client in this process, not copied: `scripts/council/mcp.ts` is not edited for them. They keep the council's authority (no token, never the hearth). A forwarded call has no time limit of the bridge's own; the SDK client's default would cancel a review after 60 s.
- The SDK's stdio transport does not notice the end of input. `serveHearthMcp` does, and ends the calls still waiting. It never closes the council (`keepCouncilOpen`), also when the client has died outright and the SDK closes the server over a broken pipe: a review begun with `council_start` runs to its end and the process leaves then. A synchronous `council_review` whose caller has gone is cancelled. What the SDK reports out of band goes to stderr, one bounded line of printable ASCII each, and a line that cannot be written (the client's end of stderr is gone too) is dropped, not thrown. None of this helps when the client's platform ends its child processes with it: the server is then simply gone.
- Registered: `forge_sessions_list`, `forge_runs_list`, `forge_run_get`, `forge_events_query`, `forge_queue_list`, `forge_reservations_list`, `forge_smiths_list`, `forge_config_get` (any session); `forge_council_start`, `forge_council_cancel` (operator). Not registered yet although their routes are mounted: the queue actions (approve, queue, pause, resume, reassign) and the shift rows (`GET /shifts`, `POST /shifts/:id/stop`), which are `x1gs.3.13`. Not registered, because no route is mounted: starting a shift, run replan, bead propose, friction add, event note.

## Notes

- Tests: `bun test scripts/hearth`. `supervisor.test.ts`, `api-spawned.test.ts` and `mcp.test.ts` start real `bun` child processes.
- A temp root used as a hearth root in a test needs a planted `.git`: the OS temp directory can sit inside a checkout, and the ledger's workspace would otherwise be that checkout.
- `server.ts` and everything it imports load no Vite module, so `bun build --compile scripts/hearth/server.ts` works (the sidecar, x1gs.9.1). Its `.env` files are read by `loadDashboardServerEnvironment` (`scripts/dashboard/server-environment.ts`) with built-ins only, as Vite's `loadEnv` read them. `server-environment.test.ts` checks both: the hearth's import graph, and each file form against `loadEnv`.
