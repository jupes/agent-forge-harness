# AGENTS.md — scripts\hearth

The hearth: the standalone loopback control-plane server (`bun run hearth`), its Vite integration, and the MCP server that is its client (`bun run hearth:mcp`).

## Scope

- Applies to this directory and descendants unless a deeper `AGENTS.md` overrides it.
- Parent guidance still applies unless this file states a stricter override.

## Local Rules

- Every request passes `gate.ts` (`frontDoorOrigin`) before routing: loopback peer; `Host`, `Origin` and `Sec-Fetch-Site` each sent at most once (counted in `rawHeaders`); loopback `Host`; `Origin`, when sent, equal to the host origin; `Sec-Fetch-Site`, when sent, `same-origin` or `none`. Do not add a route that skips it.
- The operator API is one table: `api.ts` is the runner; `routes/operator.ts` assembles the table and holds the actions and the stream row; `routes/operator-reads.ts` holds the read rows; `routes/beads.ts` holds the tracker writes and the options row; `routes/queue.ts` holds the queue actions; `routes/shifts.ts` holds the shift rows, and `shift-launcher.ts` the shifts the hearth starts. A new route is a new row. Never check the origin, the token or the audit row inside a row, and never answer JSON from one: the runner does all of it, for every row, in one order (same-origin, token, body, validation, `operator.action`, effect).
- Every mutation is an action row. `routes/council.ts` and `routes/dev-api.ts` only read; do not add a POST branch to either. Their tests mount them on their own `node:http` server; an action row is tested through a hearth (`testing.ts` gives a hermetic one), and `api.test.ts` iterates the table: a row with no fixture there fails the suite.
- Handlers in `routes/` keep the `(req, res, next)` shape and the `{ ok, data, error }` envelope.
- State lives in `AGENT_FORGE_HOME` (default `~/.agent-forge`): `hearth-<hash(root)>.lock`, `tokens/<hash(root)>.token`, the dashboard sessions beside it (`tokens/<hash(root)>.sessions.json`, hashes and expiry only, written owner-only as the token file is (below), kept when the hearth closes) and where a running dashboard listens (`dashboards/<hash(root)>.json`, no secret, removed when it closes). Tests must pass a temp `home`; never touch the real one. The event ledger lives in the same directory (`ledger.db`, `backups/`, `hook-probe.jsonl`); `scripts/agent-forge-home.ts` resolves it for both, and an `AGENT_FORGE_HOME` that is empty or only whitespace counts as unset.
- `vite-plugin.ts` and what it imports (`supervisor.ts`, `lock.ts`, `home.ts`, `gate.ts`, `paths.ts`, `loopback.ts`, `follow-tracker-writes.ts`, `launch.ts`, `token.ts`, `scripts/dashboard/dashboard-url.ts`) are loaded by Vite under Node: no `bun:` module and nothing from `scripts/ledger/` there (`launch.ts` imports only the ledger's types). `server.ts`, `api.ts`, `stream.ts` and `routes/` run only under Bun, and `server.ts` and the two `routes/operator*.ts` modules import the ledger. `paths.ts` is also bundled for the browser (`docs/js/operator.ts`): constants only.
- A council run's event stream (`GET /council-api/runs/:id/events`, `routes/council.ts`) sends the whole job as a `snapshot` on every update, unless the client asks with `?deltas=1`: then the whole job once and after it `delta` messages with only what changed since the job that client was last sent (`scripts/council/job-delta.ts`: the events and discussion rounds appended, and the other fields that changed or went away), or a `snapshot` again for an update that is not that job plus appended entries. `applyCouncilJobDelta` rebuilds each job a snapshot client is sent. The dashboard's council page does not ask for deltas yet (`agent-forge-harness-bj90`).
- Council runs started through the hearth are recorded only when `createHearth` is handed `councilLedger`. `main()` hands it `operatorCouncilLedger()` (loaded by a dynamic import); a test hearth is handed none and records nothing unless the test asks `testing.ts` for one (`councilRuns`). That builder attributes a run to the workspace and the bead the request named and infers nothing: the operator started it, not the agent session whose mirror file is in the checkout. A request whose source is a bead names that bead: the council route takes the bead for its audit row and for the service from `councilBeadId`, after `assertCouncilInput` has refused a `beadId` that is not exactly that id.
- A run the hearth starts on a bead source posts its verdict back to that bead when it completes (`routes/council-verdict.ts`, `x1gs.7.2`). The start row hands the run to `postCouncilVerdict`, which waits for it (`service.wait`, after the answer has gone) and makes one `bd comments add --json -- <bead> <text>` through the operator API's `runBd` with `commentOnBead` (`routes/beads.ts`), the comment row's own write: never repeated, confirmed by what `bd` printed, then `bead.transitioned` (`comment`). The text is `review: COUNCIL <run id> <OUTCOME> — findings <b>/<h>/<m>/<l> (blocker/high/medium/low)`: the outcome is the ledger's for the run (`councilOutcome`), in capitals, so the comment and `council.run.finished` agree, and the counts are the run's aggregated findings by severity. What posts nothing: a failed or cancelled run (no verdict, so nothing that could be read as one), a run of another source that names a bead only to be recorded against it, and a run started outside the hearth (the CLI, the council's own MCP tools). No second audit row: the start's, against the bead, says who asked. A comment `bd` refuses, or one whose outcome is not known, is not tried again and records nothing more. In a test hearth the write goes to `h.bd` (the API's recorder), not `h.commands`; `routes/council-verdict.test.ts` holds what each end of a run posts.
- A hearth serves exactly one root. A dashboard reuses a live hearth only when the lock's root matches.
- The token is minted at start and enforced by the runner on every action row. It is honoured only while the file the lock names still holds it; the token route answers 503 whenever no token could be honoured.
- The token route serves the token only to a request that passes the front door, declares the hearth's own origin and carries both halves of one dashboard session (`launch.ts`, `x1gs.3.31`): its cookie and its key in `x-agent-forge-session-key`, sent once; without either, or with one session's cookie and another's key, it is 401 with `NO_SESSION_ERROR`. The token file (readable by the hearth's OS user only, below) is the root of trust: `POST /launch` mints a one-time launch secret (256 bits, 5 minutes, single use, only its hash kept, in this process) for a request that sends the operator token once; `POST /session` exchanges it, same-origin, with the secret sent once in `x-agent-forge-launch`, for the cookie (a fresh 256-bit value, `HttpOnly; SameSite=Strict; Path=/__agent-forge`, no `Domain`, no `Secure`, no expiry: a browser-session cookie, named `agent_forge_session_<hash(home, root)>`) and, in the answer's body, the session key (another fresh 256-bit value). The page keeps the key in its origin's `localStorage` (`agent-forge-session-key`) and reads it there for every token request, never into memory: a launch in another tab replaces both halves, and every tab follows. Every request to `/session` that presents a secret spends it before anything else is looked at (`server.ts` calls `spend` ahead of the front door), whether or not the exchange succeeds; secrets, cookie values and keys are compared as SHA-256 digests with `timingSafeEqual`, every stored entry compared. Sessions are stored as the hashes of both halves (file version 2; a version-1 file, whose sessions had no key, holds none) and last 7 days from the exchange (not extended by use); they are read from their file on every check, so a hearth started again honours them. The key is never logged, never in an audit row, never in a URL.
- Why the key: a browser sends a cookie to every port of its host (cookies are scoped by host and path, never by port), and SameSite=Strict counts another port of `127.0.0.1` as the same site. So a page that another program, another OS user's included, serves on another loopback port can ask its own server's `/__agent-forge/…` path and have that server receive the session cookie's value; from a raw client with a forged `Origin` it could then ask the real token route. That page cannot read the dashboard origin's `localStorage` (an origin includes its port), so it never has the key (`tests/e2e/cross-port.spec.ts` steals the cookie that way and is refused). Mint and exchange each write an `operator.action` row (`dashboard.launch`, `dashboard.session`) that holds the action and the surface, nothing of a secret, a session or the token; a row the ledger did not store refuses with 503. Scripts, CLIs and `mcp.ts` keep reading the token file. The launcher (`vite-plugin.ts`'s `api.launchLink`, printed by `printDashboardUrlPlugin`) and `bun run dashboard:open` (`dashboard-open.ts`) mint through `requestLaunch`, over `loopbackExchange`. The future desktop shell (`x1gs.9.1`) must open the dashboard through the same launch flow.
- A launch link names the address the dashboard bound, `http://127.0.0.1:<port>/` or `http://[::1]:<port>/` (`dashboardUrl` writes a wildcard bind as its family's loopback address), never `localhost` or any other name: every link is built through `launchBase`, which refuses any other host, and `api.launchLink` checks the base before it mints. A name that resolves lets another listener answer the link: a browser may resolve `localhost` to `::1` first, the dashboard binds `127.0.0.1` only, and any program, another OS user's included, can listen on `[::1]:<port>`, be handed the link, read the secret from `location.hash` and exchange it first with a forged `Origin`. The fragment keeps the secret out of server logs, not away from whichever server answers the link. The dashboard record and `--url` go through the same check. The cookie is then kept for that address; `localhost` and `127.0.0.1` are different sessions to a browser.
- A page on another loopback port is same-site, so the browser sends its requests the session cookie (per host, not per port; SameSite=Strict does not stop it). It has no key, and the front door stops it besides: its fetch declares another `Origin` and its no-cors fetch and navigations say `Sec-Fetch-Site: same-site`, all 403 (`tests/e2e/cross-port.spec.ts`). The dashboard's dev server answers no CORS (`server.cors: false` in `vite.dashboard.config.ts`): Vite's default reflected a loopback `Origin` in `Access-Control-Allow-Origin`, which let such a page read what the dev server serves (the Beads snapshot, source files, proxied hearth answers). Keep both layers: do not turn CORS back on, and do not weaken the front door's `Origin` or fetch-metadata checks on the token route.
- The token file and the sessions file are readable only by the OS user who started the hearth, wherever its home is (`writeOwnerOnly` in `token.ts`, which `createToken` writes through; `x1gs.3.36`). On POSIX the `tokens` folder is 0700 and each file 0600. On Windows, where modes mean nothing (a file there only inherits the ACL of the folder it is created in, which outside the profile often lets every user read), the folder and each file get an explicit DACL (`acl-windows.ts`, advapi32 through `bun:ffi`): protected, so nothing is inherited from the folder above; full control for the user's SID, read from the process token, and for SYSTEM, and nothing else; the user as owner; on the folder, inherited by what is created in it. SYSTEM is in it because the system's own services run as SYSTEM, and SYSTEM reads any file through its backup privilege whatever the DACL says. Each write sets the folder's DACL first, then the temp file's while it is still empty, then writes the content and renames, and reads each back, the renamed file too: a DACL that is missing, not protected, inherited, or that names anyone else, or an owner other than the user, is refused. Setting the folder's DACL also replaces what the files already in it (a sessions file from before) inherited from the folder above. Where the DACL cannot be set or does not read back owner-only (a drive without ACLs, such as FAT32 or exFAT; a folder whose DACL the user may not change), nothing is written, and the error names the path, the reason and the fix (`OWNER_ONLY_FIX`: the default home, or an `AGENT_FORGE_HOME` on NTFS). There is no fallback. The hearth's start then fails with that error, naming its home, and leaves no lock and no token: `bun run hearth` prints it and exits 1. The dashboard starts the hearth with its output ignored; when the hearth exits with an error before it answers, the dashboard says so at once, with the exit code and how to see why (`bun run hearth` with the same `AGENT_FORGE_HOME`), not after its start timeout. A home the hearth would refuse (below) the dashboard refuses first, in the same words. The path is handed to Windows as it is, with no `\\?\` prefix: a home whose token path is longer than `MAX_PATH` (260 characters) can fail to have its ACL set or read, and is then refused like any other folder that cannot be made owner-only; nothing is written. `acl-windows.ts` looks `bun:ffi` up (`process.getBuiltinModule`) instead of importing it: Vite loads `token.ts` and `launch.ts` under Node, where a `bun:` import fails as the module loads (the import boundary `scripts/council/ledger-events.test.ts` holds). Under Node the lookup finds nothing and every Windows owner-only write refuses; only the hearth, under Bun, writes a secret. So the dashboard record (`dashboards/`), which the dashboard writes under Node and which holds no secret, is written by `writeNonSecret`: the same temp file and rename, the same modes on POSIX, and on Windows the ACL its folder gives it, as before. The Windows tests in `token.test.ts`, `acl-windows.test.ts` and `home-guard.test.ts` run only on Windows, which CI does not run yet.
- The home itself must be writable by no one but the hearth's user, SYSTEM and the Administrators (`home-guard.ts`, `x1gs.3.36`). A client finds the hearth through the lock file in the home and sends the operator token to the port the lock names, and the health check it asks that port first is passed by anything that echoes the pid and root the lock names. So whoever can write the home, or the lock file, can name a port of their own and be sent the token. One check, `homeWriteProblem(home, lock)`, refuses: on Windows an allow entry for anyone else (CREATOR OWNER counts as the user; OWNER RIGHTS only while the owner is trusted) that grants `FILE_ADD_FILE`, `FILE_ADD_SUBDIRECTORY`, `FILE_DELETE_CHILD`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER`, `GENERIC_WRITE` or `GENERIC_ALL` (for a file, the same bits: `FILE_WRITE_DATA`, `FILE_APPEND_DATA`, …), inherited or not, inherit-only or not; an owner who is someone else; no DACL. Deny entries are not counted. On POSIX a home or lock file that is group- or world-writable, or owned by another user than this one or root. The answer names the path, who can write it and with which rights, and the fix: the default home, or the commands that make the folder the user's own (`icacls "<home>" /inheritance:r /grant:r *<user SID>:(OI)(CI)F *S-1-5-18:(OI)(CI)F`, then `icacls "<home>" /remove:g *<SID>` for each trustee with an entry of its own, and `/setowner` for a foreign owner; on POSIX `chmod 700`), or, for a lock file, to delete it. The hearth makes this check first at start (`ensurePrivateHome`), before it reads or writes anything in the home, and exits 1 with it. `requestLaunch` (`dashboard:open`, the dashboard's launch link, the browser suite) makes it before it sends the token; the dashboard's supervisor before it trusts a lock, so before the proxy forwards a page's requests, the token with them, to the port; the MCP server for each lock it reads, and a lock in such a home is listed as found and not used, with why. A home the hearth creates is created owner-only: on POSIX `mkdir` with mode 0700; on Windows a folder beside it given the owner-only DACL and renamed into place, so it never exists with another ACL. An existing home is never changed: the folder may hold other things, and setting its ACL would reach them. The default home, `~/.agent-forge` in the user profile, normally grants only the user, SYSTEM and the Administrators and passes; `home-guard.test.ts` reads this machine's without changing it. Under Node (the dashboard's Vite) the Windows check runs this same function under Bun in a child process (`checkHomeInBun`: `bun scripts/hearth/home-guard-cli.ts <home> [<lock>]`, exit 3 with the refusal on stdout, with the `bun` that `bun run` names in `npm_execpath`, else the one on `PATH`); a child that cannot run is a refusal. The entry is a file of its own because Vite bundles `home-guard.ts` as CommonJS, where an entry check's `import.meta` is empty. Tests must give a hearth a home of the user's own: on Windows the OS temp folder can let others write what is created in it (this machine's grants a sandbox's group Modify), so the test preload gives the run a temp folder of its own (`TEMP`/`TMP`), and `privateTempDir` in `testing.ts` makes one in a process that did not preload it. Not covered: the folders above the home; a home inside a folder that others may rename or replace is not protected by the home's own ACL.
- `routes/council.ts` checks the token itself on its stored-run reads (`/council-api/runs`, `/runs/:id`, `/runs/:id/events`): a run holds what was reviewed, a bead's private text included (`x1gs.7.7`). The token must be sent once (counted in `rawHeaders`) and is checked before the run is looked up, so an id no run has is refused alike. `councilHttpHandler` takes `expectedToken` with no default. `/council-api/profiles` needs only the front door. The token route serves the token only to a page with a dashboard session (above), so a local program that sets the hearth's `Origin` gets no token from it; one that can read the token file (the operator's own user) is not stopped, and is not meant to be.
- `createHearth` listens, takes the lock and writes the token file as one step. When any of it throws, a lock this start took is released and the table, the council service and the server are closed before the error is rethrown: nothing of a failed start keeps answering.
- The hearth opens its ledger with no wait on another connection's lock (`LEDGER_FIRST_OPEN_WAIT_MS`), through `hearthLedger` (`routes/operator-reads.ts`): its appender (audit rows, and the outcomes the rows record), every read row that reads the ledger (sessions, a run, events, reservations, eligibility, scoreboard) and the stream. The ledger's own first open waits 2 s, synchronously, in each of its statements and attempts. So on a new ledger file another connection holds the write lock on, an action is 503 in under a second (the runner's three attempts are the wait), a read row answers its error envelope (500, or 502 for eligibility) and the stream 503 in about 30 ms (measured on Windows), and the serving thread is free meanwhile. A new ledger read here goes through `hearthLedger`: `api.test.ts` holds the lock on a new file and times every read row and the stream.
- Under Bun's `node:http`: a header sent twice arrives as its last value (only `rawHeaders` shows the repeat, which is why the runner counts there); a client that disconnects closes the request and the socket but not the response (which is why `stream.ts` and the council run stream in `routes/council.ts` listen to all three); response headers are not sent until the first write unless `flushHeaders()` is called; `res.write` returns true however much is waiting, so `res.writableLength` is what `stream.ts` reads for backpressure; `drain` can fire inside a `write`, before the caller's next line, so the stream's pump refuses to be re-entered; ending a response to a client that is not reading frees nothing until that client leaves, so a stalled stream's socket is destroyed instead; and leaving `for await (const chunk of req)` early makes the runtime end the response itself with an empty 200, so the runner's body reader (`requestBody` in `api.ts`) reads with listeners, takes them off when it stops, and pauses a body that has not ended.
- An action's body is read under a time limit (`BODY_TIMEOUT_MS`, 10 s; a test passes `api.bodyTimeoutMs`). A body that has not ended by then is answered 408, or with the refusal the request already had, and its connection is closed once the answer is written. A refusal given before the body is read (the origin, the token, a declared length over the cap) is sent once the body has been read and dropped: under Bun an answer sent while a `Connection: close` client was still writing a body of 2 MB or more was not received at all (measured on Windows; 256 kB was). A request that says `Expect: 100-continue` is never answered `100 Continue` by the runtime: `server.ts` listens for `checkContinue` and hands the request on, and the runner sends `100 Continue` on the first read that keeps the body (`requestBody` in `api.ts`), which comes only after every check the head can answer. So such a client (the MCP server, below) is refused on its head with its body never asked for. Anything else that reads a body must send it too (nothing does today). A refusal whose body has not begun to arrive within 50 ms (`HELD_BODY_MS`) is sent then, for such a client and for one that holds its body back without saying so; the body is read and dropped after it, and the connection closed at the time limit if it never ends. Accepted, not handled: a client that holds its body back without `Expect` for longer than that and then sends a large body with `Connection: close` can still lose the refusal; and an answer outside the table (the front door's 403, a 400 for the path, a 404 or 405, the token and health routes) is sent without reading the body, so a client that sent its body unasked can lose it, and a body there that never ends holds its connection until the client leaves.
- `bd` is never run synchronously here. `bdRunner` is asynchronous, takes an argument array and no shell, and never rejects: an argument the runtime will not pass on (one holding a NUL, a command line past the platform's limit) makes `execFile` throw before anything starts, and the runner resolves that with no exit status and a reason of its own, which names the runtime's error code when there is one and never the arguments (the runtime's own message for a NUL repeats the argument). Nothing is sent on the child's standard input, and the runner ends it at once: a `bd` that reads it (`create --description=-`) reads nothing and goes on, instead of waiting for the runner's limit. Its tests start `process.execPath` as a stand-in, never `bd`. The checkpoint review refuses a note holding a NUL before anything is recorded; its note limit keeps the comment far under a command line's. The queue read is always the same argument array (`QUEUE_LIST_ARGS`), one at a time, with its own 15 s limit passed to the runner; every other call has the runner's 30 s. The council service is the one other thing here that starts `bd`: for a bead source it runs `bd --readonly show` and `bd --readonly comments` (a `pr` source started here reads no bead: looking up a PR's linked beads is the CLI's `--linked-criteria` alone, `x1gs.7.4`), through the council's own runner (asynchronous, an argument array, no shell, 30 s). `createHearth` wraps that runner in `hearthCouncilRunner`: `bd` runs in the checkout that holds the tracker (`localStateRoot`, as the hearth's own `bd` does), `git` and `gh` in the hearth's root. The `runBd` a test hands the API does not reach the council: `councilRunCommand` does, and `testing.ts` always hands one in, a recorder (`h.commands`) that refuses whatever its test did not arrange, so no hearth test starts a real `bd`, `git` or `gh` through the council.
- A write to the tracker (`routes/beads.ts`) is one `bd` call, never repeated, never with `--repo`. Build its arguments so that nothing a caller sent can be read as an option: every value as `--flag=value`, every positional after `--` (`bd comments add <id> --help` prints help, exits 0 and adds nothing), an id always present (`bd close` with none closes the last touched issue) and checked with `parseBeadsIssueId`. A description of exactly `-` is refused: `bd` reads it from standard input, which `bdRunner` ends at once, so the issue would be made with no description.
- `tracker-write.ts` is what every write to the tracker shares (the bead-id check, reading what `bd` printed, its refusal line, the never-started test, storing the outcome event). It has no runtime import from `routes/`, so `scripts/scheduler/queue.ts` uses it without loading the read rows. Keep it that way.
- The queue rows (`routes/queue.ts`: `POST /queue/:id/propose|approve|queue|pause|resume|reassign`) are a way in to `scripts/scheduler/queue.ts` as the operator, and nothing more: the table of legal moves, the lock, the `bd` calls and the `bead.transitioned` event are there (see `scripts/scheduler/AGENTS.md`). Never write a queue label from a row. The moves take an empty body; `reassign` takes `{ smith }`, checked against the configured smiths in the validator, before the audit row, whose `target` is then the smith and whose bead is the bead. A row answers `404` for an id no bead has, `409` when the table refused, the bead is in no state, the lock was busy or another writer's label was found on the bead, `502` when `bd` refused, `504` when the outcome is not known, and never `403`. `propose` (`x1gs.5.10`) is the way in for a bead outside the queue or one carrying a queue label the queue did not write (a child's inherited label): it ends at `proposed`, so the bead still waits for the operator's `approve`; a bead in a state, with two labels, or closed is refused `409`. `resume` of a bead paused while running puts it in `queued`, not `running` (`x1gs.5.4.4`). The scheduler's moves (`start`, `submit`, …) have no row. The lock file is `queue-lock.db` in the hearth's home.
- The shift rows (`routes/shifts.ts`) are a way in to `forge:shift run` and to the functions `forge:shift list`, `stop` and `recover` call (`scripts/scheduler/shift-store.ts`, `shift-recover.ts`), over `<home>/shifts`: a shift given another home is neither listed, stopped nor recovered here. `GET /shifts` lists the records of this hearth's workspace, and with them the starts of this hearth that have no record (below), newest first by `startedAt` (ISO 8601 to the millisecond, so two starts can tie). A tie is broken the same way every time (`newestFirst`): a start with no record before a record, starts by launch order in this hearth (the later first, a sequence number the registry keeps), records by id, descending. Never leave a tie to the sort: a test of the order stamps its starts with one instant (`api.shiftNow`). `POST /shifts/:id/stop` takes an empty body and writes the stop request; the shift itself stops its runs, gives their beads back and records `shift.stopped`, so the row's only ledger row is its audit row. `404` for no such shift or another workspace's, `409` for one that has stopped. `POST /shifts/:id/recover` (`shift.recover`) takes an empty body and runs `recoverShift` with the hearth's `bd`, ledger appender, queue lock and main checkout (`localStateRoot`): for a shift whose process ended without stopping it, it releases the beads the shift still owns to `queued` as the scheduler, frees the reservations of its worktrees, and records `shift.stopped` (`recovered`); see `scripts/scheduler/AGENTS.md`. `400` for an id that is not a shift's (no audit row), `404` for no such shift or another workspace's, `409` for one that has stopped, one whose process is alive (a pid reused by another program reads as alive too), one whose record recovery cannot read (`unreadable`) or one another recovery holds, `502` when the recovery lock or the ledger cannot be used, or when the recovery did not finish (the error says what is left; the record stays `running` and a second recover finishes it). A stop or a recover of a start of this hearth that has no record yet is `409` (`is still starting`), with no stop request written and nothing recovered.
- `POST /shifts` (`shift.start`, `x1gs.5.4.5`) starts `forge:shift run` as a child of the hearth (`shift-launcher.ts`). The body is flat and strict, every field optional, each named as the CLI's flag in camel case: `for`, `runTimeout` (durations as the CLI takes them: `90s`, `30m`, `2h`), `concurrency`, `maxBeads`, `maxUsd`, `repairs` (JSON numbers), `epic`, `smith`, `base` (strings); `{}` takes every default; any other field (`filter` too) is `400`. The validator checks each field's JSON type and nothing else of its own: it turns the fields given, and only those, into the flags the child gets, parses them with the CLI's own `runOptions` and checks the result with `shiftOptions`, so a value the CLI would refuse is `400` before anything is recorded, and a field left out is left to the CLI's default: the config's `[shift]` value as the child reads it (`agent-forge.toml` in the hearth's root over `config.toml` in the hearth's home), else its builtin (`x1gs.5.4.7`, `scripts/config/AGENTS.md`). Only a smith's name is checked here, not that it is configured: the child refuses an unknown one, and the start is listed `failed`. A string value that reads as a secret (`looksLikeSecret`; a smith or a branch name may hold a `ghp_…`) is `400`: every value goes on the child's command line and back in each listing of the start. Once the body is good the shift id is minted (`mintShiftId`, past any id a record, a stop request, a launch or another mint not yet started has), so the audit row's target names the shift; the child gets it as `--id`, and refuses an id a record or a stop request in the home already has. The child is `[process.execPath, scripts/scheduler/shift-cli.ts, "run", "--id", <id>, ...flags]`, an argument array, in the hearth's root, with the hearth's own environment (`process.env`) and `AGENT_FORGE_HOME` set to the hearth's home: the same ledger, queue lock and shifts directory. It is started by `superviseShift` with `Bun.spawn`, not through `supervise()` (`scripts/executors/supervisor.ts`), which is made for a provider run (a prompt on stdin, stdout read a line at a time, a time limit). What `supervise` gave is kept: the tree guard (`guardTree`) for a hearth killed outright, `killTree` for the whole tree, an `exit` hook that ends the tree of every shift still running when the hearth exits by a way that skipped `close()`, and, outside Windows, a process group of its own (a terminal's Ctrl-C reaches the hearth, not the shift). No time limit of the hearth's own. Answers `202` with the start (`shiftId`, `state: "starting"`, `pid`, `alive`, `workspace`, `startedAt`, `requested`: the fields given) and the paths that stop and recover it. `409` while another start of this hearth has no record yet (one start at a time: a second would be a double submit, or the same fetch failing twice; two shifts running at once is fine), and for an id this hearth has started already (two requests that minted it at once: the second starts nothing), `502` when the child could not be spawned, `503` when the hearth is closing; each after its audit row, as a refused effect always is. The operator token stops a page of another origin, a request that cannot set headers and, since the token route needs a dashboard session (`x1gs.3.31`), a local program that only declares the hearth's origin; a program that can read the token file can start a shift, as it can a council run. The answer does not wait for the shift: its base is fetched first (up to git's 2 minute limit), and its record is written after it.
- What the hearth knows of a shift it started is in memory (`createShiftStarts`) and is gone when the hearth stops. Until the child has written its record the start is listed by `GET /shifts` as `{ shiftId, state: "starting", pid, alive: true, workspace, startedAt, requested }`; from then on the record is what is listed, exactly as for a shift the CLI started. A child that exits with no record (no origin, offline, an unknown smith, a config it cannot read, a crash) is listed as `state: "failed"` with `exitCode`, `endedAt` and `error`: the error the shift printed in its `{ ok: false, error }` envelope on stdout, else the end of its stderr (the line that announces the id dropped), with secrets redacted (`redactSecrets`) and at most 500 characters. Only the newest 20 failed starts are listed (`KEPT_FAILED_LAUNCHES`); stdout is kept to its last 16 kB and stderr to the supervisor's tail. A child that exits after writing its record is forgotten: its record says how it ended.
- `close()` ends the shifts this hearth started, last, once the server has closed: each one still running is asked to stop (`requestStop`, as `POST /shifts/:id/stop`) as soon as its record exists, the hearth waits up to `SHIFT_STOP_GRACE_MS` (30 s; a test passes `api.shiftStopGraceMs`) for every one to exit on its own (each puts its beads back in `queued`, frees its reservations and records `shift.stopped`), and then ends what is left with its process tree (`stop()`). A shift ended that way leaves its beads `running` and its record `running`; `forge:shift recover` (or the recover row of the next hearth) gives them back. A start that arrives once closing has begun is `503`. `SIGINT` and `SIGTERM` run all of it: `main()` installs `closeOnSignal` (`server.ts`), which runs `close()` and then exits 0. It makes the hearth the process's interrupt owner (`ownInterrupts`, `scripts/executors/AGENTS.md`, `x1gs.5.4.14`): the supervisor's own handler, which a child run through `supervise()` in the hearth's process installs and which would kill every supervised child and exit 130 at once, leaves the signal to the hearth, and what `supervise()` started is ended by its exit hook once the hearth exits. Nothing else in the hearth may listen for those signals and exit first. `shift-launcher.test.ts` runs a hearth in a child process, emits each signal, and checks the shift got its stop request and the hearth exited 0, with and without a child run through `supervise()` in it (the hearth runs none today; that test is the guard for one that would). A second `SIGINT` or `SIGTERM` while that close waits does not wait: it ends the tree of every shift still running at once (`endLiveShifts`) and exits 130 (`INTERRUPTED_EXIT`, as an interrupted command does); those shifts need `forge:shift recover`. A hearth that exits another way without closing (an uncaught error, a `process.exit`) ends its shifts' trees from the launcher's `exit` hook. `shift-launcher.test.ts` covers the second signal, that exit with the tree guard taken away, and a hearth killed outright with only the tree guard left, each with a shift whose own child must die too. What does not get there: a hearth ended with no chance to run code. On Windows that is how the dashboard ends it (`stopIfOwner` calls `process.kill`, which is `TerminateProcess` there and runs nothing in the hearth), and `SIGKILL` elsewhere; the tree guard then ends every shift the hearth started, at once, with its beads `running` and its record `running`, and each needs `forge:shift recover`. No signal handler can change that: none runs. And on Windows a Ctrl-C in the console the hearth runs in is delivered to every process attached to it, the shift included, which then stops itself as a CLI shift does on its first Ctrl-C (`scripts/scheduler/AGENTS.md`), while the hearth's close asks it to stop as well; a second Ctrl-C ends both at once and the shift needs a recover. That console case is inferred from the two halves, each tested with an emitted signal; no real console Ctrl-C has been sent in a test.
- A test hearth (`testing.ts`) is handed a stand-in launcher (`h.shifts`, `fakeShifts`): it records each launch (`spec`: argv, cwd, env) and starts nothing, its children run until the test lets them exit or the hearth ends them, its ids are minted in order (`h.shifts.next()`), and its grace is 200 ms. No hearth test starts `shift-cli.ts`: its real dependencies run `bd` in the main checkout and `git fetch` against origin. `shift-launcher.test.ts` starts real children through `superviseShift`, with a stand-in script written to a temp directory in place of the CLI.
- `GET /queue` marks each entry `backed`: whether the issue's own `queue_state` metadata names the entry's state, which is how the queue's own labels are told from one a child inherited. It also carries the bead's `smith` metadata and, for a paused entry, `resume`: where `resume` puts it, from its `queue_resume` when that names a state it was paused from (that state, or `queued` for `running`).
- `GET /eligibility` answers `readEligibility` (`scripts/scheduler/eligibility.ts`) for the hearth's root, with the shift records of its home (`<home>/shifts`): which queued beads may start and why the others wait. A queued bead that a shift's worktree still holds waits with `waitsOnShift` naming that shift (`x1gs.5.4.13`). A read is two `bd list` calls, one `bd show` when a bead outside the queue holds a reservation, and one record read (and pid check) per shift whose worktree holds a queued bead's reservation; coalesced; `502` when `bd` fails; not a stream collection.
- `GET /beads/counts` answers the dashboard's four Beads cards (`BeadCounts`): one `bd export` (`BEAD_COUNT_ARGS`, always the same array), counted by the snapshot builder's own rules (`scripts/beads-dashboard.ts`), so a card means what it meant when drawn from a snapshot. Coalesced like the queue read, with the runner's 30 s; `502` when `bd` fails; not a stream collection: the call prints the whole tracker (measured: about 2 MB and 1.3 to 2.7 s for 767 issues), so it is made when a page asks.
- `GET /scoreboard` answers `readScoreboard` (`scripts/ledger/scoreboard.ts`) for the hearth's workspace, the function `forge:audit --scoreboard` prints; its one parameter, `since`, is judged by `parseAuditArgs`. `routes/scoreboard.test.ts` compares the route with the CLI run as a child from the hearth's checkout. Not a stream collection. `forge_scoreboard_get` reads it for any session, a workspace row with `since` as its one argument; the hearth, not the tool, says whether a `since` is ISO 8601.
- Exit 0 from `bd` is not success. Confirm a write by what `bd` printed, take the id it printed as the bead that was written, and only then append `bead.transitioned`. Answer `502` when `bd` refused, with its error line and not everything it printed: before it refuses, `bd` can print a warning that repeats the title it was given; with `--json` some commands print the error on stdout; and the runner's `Command failed: bd …` line on stderr repeats every argument, so never pass that on. Answer `504` when the outcome is not known (a killed `bd create` still creates the issue), and for a create whose printed description is not the one that was sent (none when none was): `bd` made that issue, so the answer names it, and the page does not invite a second create after a `504`. Answer `409` for a close or a claim that changed nothing (`bd` exits 0 for an issue that was already closed, or already claimed by the same actor, and the time it prints is then from before the call began), and never `403` from an effect: the page posts an action again after a 403. Two seconds are allowed for the second `bd` rounds to, and they are a window, not a proof: a close repeated with the same reason inside them is answered and recorded as a close, and so is a claim made within two seconds of the issue's last change (the claim before it, or an edit), because the time read for a claim is `updated_at`, which any change moves. Do not read `started_at` instead: `bd` writes it only while it is empty, so a bead released and claimed again prints the time of its first claim, and that claim, which did change the bead, would be answered `409`.
- A call with no exit status is "`bd` could not be started, nothing was changed" only when stdout is empty and stderr is, whole and alone, the runtime's own message that there is no such program. Never decide it by searching stderr for a word: a `bd` that started prints warnings of its own, and a warning can hold any word, the title it was given included. Everything else with no exit status is a `504` that says the call was stopped before it answered or never started, and not which: a call killed at the runner's limit and one the runtime could not spawn for another reason (its working directory gone, which Bun reports as `ENOENT: no such file or directory, uv_spawn 'bd'`) look alike there.
- `bd-answers.ts` is what `bd` prints for a write, in one place: `testing.ts`, the browser suite's stand-in and the route tests all build their answers from it. Change it there, and check a change against a real `bd`.
- Under Vite the peer is always the dev server, so the loopback check for proxied traffic is `guardRequest` in `vite-plugin.ts`. Keep it failing closed.
- Vite's proxy ends the client's response only when the hearth's answer ends cleanly. When the hearth's socket closes mid-answer (a killed hearth), it left the client's response open, and a page's event stream heard nothing until its 45 s silence limit. `closeWithUpstream` in `vite-plugin.ts` destroys the client's response then. It tells a cut-off answer by `readableEnded` at `close`, not by `complete`, which Bun has already set to true there. `vite-plugin.test.ts` shows it with the page's stream client and a TCP relay between the proxy and the hearth whose connections the test cuts. The other way round, the proxy aborts its request to the hearth only on the client request's `aborted` event, which Node emits only for a request whose body had not ended: a GET the page gave up before the hearth answered (a hearth that hangs) left the connection to the hearth open. `dropWithClient` destroys the proxy's request when the client's response or socket closes before the hearth's answer has ended. Its test runs the dashboard under Node in a child process (`nodeDashboard` in `vite-plugin.test.ts`): under Bun's `node:http` a client that left before any answer raised no event on the request, the response or the socket within 1.5 s (the socket's `close` came when the server closed; Bun 1.3.10, Windows), so the proxy cannot tell there.
- Spawn the hearth as `bun scripts/hearth/server.ts`, never through `bun run`, so the pid in the lock is the server's.
- Under Bun, `fetch` and `node:http` send a request for `127.0.0.1` to `HTTP_PROXY` (or `http_proxy`) when the process started with one and no `NO_PROXY` entry is `127.0.0.1` or `*`, and nothing done at run time turns that off; `loopbackProxyVariable` (`loopback.ts`) holds the measured rule. So every client of a hearth here (the MCP server, the health probe, the tracker-write follower) uses `loopbackExchange`, and a new one must too. The hearth's own tests use `fetch`: `bun test` refuses to start in such an environment and says what to set (`test-preload.ts`, first in `bunfig.toml`'s preload list). Node goes direct unless `NODE_USE_ENV_PROXY` is on; the browser suite's global setup refuses that case. The dashboard's own proxy to the hearth goes direct even then (measured, Node 25.8.2): Vite's proxy makes each request with `agent: false`, a fresh agent that reads no proxy setting, while Node's `fetch` and `http.globalAgent` in the same process do take `HTTP_PROXY`. `vite-plugin.test.ts` keeps it so, with a proxy stand-in, where `node` reads proxy settings from the environment (`--use-env-proxy` in `node --help`). Never give the proxy `http.globalAgent`.
- `hearthPlugin`'s `onTrackerWrite` is how the dashboard learns that the tracker changed: `follow-tracker-writes.ts` polls `GET /events?kind=bead.transitioned` on the hearth (over `loopbackExchange`, with the hearth's own `Origin`) once a second, one poll at a time, and calls it once per poll that found new events. The first poll only takes the newest id as its cursor; a failed poll keeps the cursor, so a write made while the hearth was unreachable is still found. It stops when the dev server's HTTP server closes. It sees only writes that append `bead.transitioned` (the Beads and queue rows), never a write made with `bd` outside the hearth.

## The MCP server (`mcp.ts`, `bun run hearth:mcp`)

- It is a client of the running hearth and nothing more. A tool is a row of `FORGE_TOOLS` naming a mounted route; a call is one request to it and the route's envelope is the result, as one text item. Never answer for a route there, read the ledger or run `bd`; never start a hearth from it.
- A tool is added with its route, as a row: `authority` is `operator` exactly when the route is an action row, and `scope` is `checkout` when the route reads the hearth's own root (run state, config files, the council's directory) and `workspace` when it reads the ledger or Beads. `mcp.test.ts` iterates the table against a real hearth: a governed row needs an entry in `OPERATOR_FIXTURES`, an agent row one in `READS`, every row one in `SCOPE_FIXTURES`, or the suite fails. The refusal matrix needs nothing per tool.
- Order of a call, and it is not to be rearranged: the name; the authority rule (a governed row in a session without `--operator` is refused before its arguments are looked at); the arguments; the request; the hearth; the token; one request. `tools/list` and `initialize` are the same for every session.
- The token is read for one governed call, from the path this module computes for the verified hearth (never a path taken from a lock), must be what `createToken` writes, is sent on that request only and is kept nowhere. An agent session has no function that reads a token file. Never put the token, a header value or a byte of an answer in an error message.
- Requests go through `loopbackExchange`, a `node:net` socket to `127.0.0.1`, never `fetch` or `node:http`: under Bun both send a loopback request to `HTTP_PROXY` when the process started with one, and no request option or change at run time turns that off. The query is built by `URLSearchParams`; a path parameter must match `SEGMENT`; a request target is at most `MAX_TARGET_BYTES`. A governed row carries its route's `maxBodyBytes` (the table test compares the two) and a larger body is refused here, where the reason can be given without sending the body. A body over 64 kB is sent with `Expect: 100-continue` and written only when the hearth answers `100 Continue`, which it does once it begins to read a body it will use (the body rules above). So a refusal on the head (a token it does not honour) arrives however long the hearth takes to give it, with the body never sent, and an accepted large request waits one round trip, not a fixed time. The exchange has no fallback wait: a peer that answers neither is its time limit. Interim answers (1xx) are read past and only `100 Continue` lets a waiting body go; `101` is refused. A hearth built before the hearth honoured the expectation answers `100 Continue` at once (Bun's default with no listener), so the body goes at once and that hearth reads and drops it before it refuses.
- A lock is used only after its file name, token file, port and pid check out and its port answers the health route with that pid and that exact root; locks are found by reading the home and comparing real paths (`realpathSync.native`), so another spelling of a checkout is the same checkout. Two live hearths for one directory: the lock that comes first by name is used. These checks tell a stale lock or a reused port from a live hearth. They are not proof against a process of the same user that takes a dead hearth's port and answers the health route with the lock's pid and root: the pid and the root are not secrets (`x1gs.3.19`).
- The council's tools are re-exported through a client in this process, not copied: `scripts/council/mcp.ts` is not edited for them. They need no token and never reach the hearth. An agent session may call only `COUNCIL_READ_TOOLS` (`council_profiles`, `council_readiness`, `council_status`, `council_replay`, `council_list`), and only while the council marks each read-only; every other council tool (`council_start`, `council_review`, `council_cancel`, and any tool the council adds) is governed: refused in a session without `--operator` before the council sees the call, with the refusal a governed forge row gives, and listed with "Operator session only." first (`x1gs.3.15`). It fails closed on purpose: put a new council tool on the read list only when it reads. A forwarded call has no time limit of the bridge's own; the SDK client's default would cancel a review after 60 s.
- The SDK's stdio transport does not notice the end of input. `serveHearthMcp` does, and ends the calls still waiting. It never closes the council (`keepCouncilOpen`), also when the client has died outright and the SDK closes the server over a broken pipe: a review begun with `council_start` runs to its end and the process leaves then. A synchronous `council_review` whose caller has gone is cancelled. What the SDK reports out of band goes to stderr, one bounded line of printable ASCII each, and a line that cannot be written (the client's end of stderr is gone too) is dropped, not thrown. None of this helps when the client's platform ends its child processes with it: the server is then simply gone.
- Registered: `forge_sessions_list`, `forge_runs_list`, `forge_run_get`, `forge_events_query`, `forge_scoreboard_get`, `forge_queue_list`, `forge_reservations_list`, `forge_smiths_list`, `forge_config_get` (any session); `forge_council_start`, `forge_council_preview`, `forge_council_cancel` (operator). `forge_council_preview` is `POST /council/preview`, an action row though it starts nothing: a bead source is read through `bd`, so an agent session is refused before its arguments are read, as for a start. It takes the fields that change a pack (`sourceType`, `source`, `maxBytes`, `redactSecrets`, `beadId`) and refuses a start's `profile`, `maxUsd` and `runId` here, which the route would ignore. Re-exported from the council: its read tools (any session) and `council_start`, `council_review`, `council_cancel` (operator). Not registered yet although their routes are mounted: the queue actions (propose, approve, queue, pause, resume, reassign) and the shift rows (`GET /shifts`, `POST /shifts`, `POST /shifts/:id/stop`, `POST /shifts/:id/recover`), which are `x1gs.3.13`. Not registered, because no route is mounted: run replan, bead propose, friction add, event note.
